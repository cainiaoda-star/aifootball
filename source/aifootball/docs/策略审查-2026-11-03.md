## 一、已经修掉的 4 个问题

### 1. 竞彩让球方向算完即弃（P0）

`RecommendationSelection.cs:402`

```csharp
if (board != Boards.Bd) r.RecHandicap = null;   // ForDisplay 里
```

`ApplyJcHandicap` 明明给竞彩算好了让球方向（`RecommendationService.cs:252`），
但 `ForDisplay` 收尾时把非北单的 `RecHandicap` 一律清空。而落库用的是 `ForDisplay` 的结果：

```csharp
RecHandicap = r.RecHandicap,                        // 竞彩恒为 null
Handicap = r.RecHandicap is null ? null : r.Handicap // 连带让球数也 null
```

**连带后果**：`SettleAsync` 算 `HandicapHit` 需要 `RecHandicap` 和 `Handicap`，
两个都是 null → 竞彩让球命中永远算不出来 → 依赖它的票永远无法结算。

查库印证：全库 48 条竞彩推荐，`Handicap` 非空的是 **0 条**。

**修法**：在 `ForDisplay` 之前把让球信息存快照，落库前回填。不动展示逻辑，影响面最小。

### 2. 出票用了展示过滤后的名单（P0，本次新功能引入）

`SaveTicketAsync` 原本从 `all[Boards.Jc]` 取腿——那是 `ForDisplay` 的结果，`RecHandicap` 已被清空，
`TicketPlanBuilder.Build` 第一道过滤就全跳过，**票永远构建不出来**。

**修法**：保留未过滤的 `recs`，出票用 `ForJcHandicap(recs)`，与 `/api/recommend/jc` 的 `hcpRows` 同源。

### 3. 票腿与推荐表脱节，票永远停在 PENDING（P0）

竞彩精选 0 场的日子，票照样会发（票腿来自「有让球方向的全部场次」），
但这些场次在 `Recommendation` 表里**没有记录**——原结算逻辑靠
`SELECT TOP 1 HandicapHit FROM Recommendation WHERE MatchId=...`，查不到 → `LineHit` 永远是 null。

**修法**：票腿自带 `PickSide` + `Handicap`（`db/10_ticket_kpi.sql` 补两列），
结算直接对 `FbMatch` 的完场比分判定：

```sql
HomeScore + Handicap - AwayScore > 0  → 让胜
< 0                                    → 让负
= 0                                    → 让平
```

推荐表只作兜底（早期没存让球数的票）。

### 4. 3 场票的过关方式写成「1串1」

`PassFor(3)` 返回 `1串1#2串1#3串1`。`1串1` 不是彩民叫法，也会让票面 KPI 把同一票型拆成两个 key。
已改为 `单关#2串1#3串1`，注数与结算不变（`ParsePassSizes` 本来就认「单关」）。

## 二、需要你决策的（没动代码）

按影响排序。

### A. 小样本否决信号 —— 我认为这是最该改的一条【已改 11-03 晚】

`HitProbabilityService.cs:181-208`，`ApplyEmpiricalGate`：

```csharp
if (total < 12 || ...) return;                      // 12 场就开始用
...
if (rate < MinFeaturedHitProbability && rec.SignalLevel >= 2)
{
    rec.SignalLevel = 1;                            // 直接踢出精选
}
```

`rate` 是「该方向 × 该水位段」的历史命中率，`total` 只有 **12 场**才有资格参与。
12 场的 95% 置信区间约 ±28 个百分点——**50% 和 55% 在这个样本量下统计上没有区别**，
但代码会据此把双信号降级成弱信号。

反差很明显：`MinFeaturedHitProbability = 55` 这条门槛本身有 **944 场**验证
（见 `RecommendationScoring.cs:11` 注释），而否决它的机制只有 12 场。

改法（三选一）：
- 把 `total` 门槛提到 40~50；
- 用 Wilson 下界代替点估计；
- 用已有的 `HitRateMath.Shrink` 做贝叶斯收缩后再判（正在给 `HitProbability` 用，唯独这里没用）。

**已落地的实现（三条都用上）**：按样本量分级，新增 `RecommendationScoring.MinSampleForConfidence = 20`、
`MinSampleForDemote = 40`。

| 样本量 | 行为 |
|---|---|
| < 20 场 | 完全不动，连置信度也不改 |
| 20~39 场 | 只按收缩值调整 `Confidence`，**不动精选等级** |
| ≥ 40 场 | 收缩后仍 < 55% 才踢出精选 |

判定值从裸点估计 `100*hits/total` 换成 `HitRateMath.Shrink(hits, total, 0.55)`——先验取精选门槛本身，
样本越少越贴近先验。60 场 33% 收缩后 45.7%（降级），60 场 66.7% 收缩后 60%（保留）。

侧记：这条改动会让「12 场就否决」的现象消失，短期内精选数量可能变多。这是**预期效果**——
旧行为的证据强度不足以支撑否决，不是因为门槛放松了。

### B. 票面概率是未收缩的乐观值

票腿的 `LegProbability` 来自 `HitRateMath.Devig`（`RecommendationSelection.cs:535`），
**没有经过 Shrink 收缩**。而 `HitProbability` 是收缩过的。

所以 `Plan()` 算出来的票面中奖率/回本率系统性偏高。今天这张票：

| 指标 | 值 |
|---|---|
| 中奖率（至少一注） | 92.7% |
| **回本率（奖金 ≥ 本金）** | **19.7%** |
| 期望回报 | 0.803 |

三条腿 58.9% / 58.2% / 57.4% 都是去水原值。收缩到 55% 附近的话，回本率会再低一截。

要么给票腿也接收缩，要么在票面标注「未收缩」。

**已落地的实现（结论与原文不同，先纠正前提再改）**

实测反驳了「模型值偏乐观」这个假设。拿 11-03 的票对比模型值和盘口值：

| 场次 | 模型 | 盘口 |
|---|---|---|
| 周二008 | 61.1% | 59.7% |
| 周二005 | 57.8% | 57.4% |

高低是混着来的，没有系统性偏向。真正的问题是**同一张票用了两套概率**：
进票的 55% 门槛按 `HandicapProbability`（模型）判，算奖金概率却用 `LegProbability`（盘口去水），
两个数都没标注来源，于是「中奖率 92.7% / 回本率 19.7%」说不清是哪个口径给的。

改法是**不用拍脑袋的收缩系数，改用保守下界**——没有让球方向的经验样本，任何 Shrink 强度都是编的：

- 新增 `JcCoverTicket.PickProbability(modelP, marketP)`：票面概率取两者较低值；
- 新增 `JcCoverTicket.Disagreement(modelP, marketP)`：两个来源差几个百分点，页面上并排显示；
- `TicketPlanLine` 加 `ModelProbability` / `MarketProbability` 两列（`db/12_ticket_leg_probability.sql`），
  `LegProbability` 从此含义变成「两者较低值」，老行不回填；
- 页面每条腿 hover 出「模型 x% · 盘口 y% · 分歧 z 点」，回本率说明改成「取低值的保守下界」。

留这两列不是为了好看：它是这套系统唯一能自证的问题——**过一段时间就能回答「模型和盘口到底谁准」**。

### C. 让球概率从欧赔推，不用真实让球盘

`ApplyJcHandicap`（`RecommendationSelection.cs:166`）用
`HandicapMath.FromOdds` 拿欧赔去水 → 拟合 Poisson → 折成让球三项概率。
竞彩让球固定奖金（`rqWin/rqDraw/rqLoss`）**已经采到了，但只用来显示水位**（`HandicapOdds`），
没参与定概率。

拿欧赔推的概率去买让球盘，两者的抽水结构不同，会系统性偏离。直接对让球盘去水更准。

**已落地的实现（11-03 晚）**

`ApplyJcHandicap` 现在同时算两套，**优先用盘口**：

| 来源 | 算法 | 用在哪 |
|---|---|---|
| market | 竞彩让球固定奖金三项 `Devig` | 定方向、`HandicapProbability`、精选门槛、出票 |
| model | 欧赔去水 → 泊松 → 折成让球数三项 | 没有让球盘时的退路 |

两个值都留在 rec 上（`HandicapModelProbability` / `HandicapMarketProbability`），
`HandicapSource` 标明这次用的是哪一个；页面上让球场次旁边挂「盘口 / 反推」小标。

为什么不再自己挑：欧赔链是「不让球三项 → 泊松 → 折算让球数」，中间夹着进球期望拟合和大小球盘校准，
链条每长一环偏差就放大一次；让球盘就是这一注的报价，抽水已经按同一市场归一。

**实测差异（11-03 19:47，21 场卡）**：14 场同向，2 场换向。换向的两场正是热门场：

| 场次 | 欧赔反推 | 让球盘去水 | 后果 |
|---|---|---|---|
| 周二009（让-2，主胜 1.13） | 让负 | **让胜 40.1%** | 撞上「必发主胜 ≥75% 极端大热」，被清掉 |
| 周二010（让+1，客胜 1.43） | 让胜 | **让负 39.9%** | 撞上「必发客胜 ≥75% 极端大热」，被清掉 |

**这不是丢场，是两条规则的正确叠加**：旧规则算出来的是冷门侧，所以躲过了大热规则；
按盘口定价之后，让球方向落在热门侧，正好被 75% 那条挡住。
代价是让球表从 8 场变 6 场——这也给「75% 阈值要不要动」提供了第一份直接证据。

### E. 赔率变化用绝对值，不是百分比

`RecommendationEngine.cs:15-18`：`OddsDrop = -0.05m`。

主胜 1.30 跌 0.05（−3.8%）和 3.50 跌 0.05（−1.4%）被当成同一个信号强度。
低赔场次的 0.05 信息量大得多。行业惯例用百分比或对数比。

**已落地的实现（11-03 晚，只做了一半，另一半故意没做）**

新增 `AtOdds(baseAbs, odds)`：取「绝对阈值」和「按水位等比换算值（以 2.0 为锚）」中**较小**的那个。

- 1.30 的「小降」从 0.05 收紧到 0.033，2.00 不变，3.50 仍是 0.05
- 平赔的 `DrawOddsPress` 同样按平赔水位换算
- `ApplyAsianConflict` 里那两处阈值也走同一函数（顺带补了 `spfHome` 参数）

**为什么高赔一侧不动**：回测出来的 53% / 30% / 55% 都是按绝对阈值统计的。

### F. 逻辑靠文案字符串匹配

| `NotFeatured` | 已明确不进精选 | 长水降权的前置闸 |
| `ALeagueAwayNotFeatured` | 澳超客胜 | 页面过滤 + 让球票剔腿 |
| `SerieABigGoals` / `StrongFavouriteBigGoals` | 意甲偏大球 / 强热门大球 | 文案只有补一次 |

替换掉的 12 处判定：`RecommendationEngine` 8 处、`HitProbabilityService` 1 处、
`RecommendationSelection.IsIssuedDraw` 3 处合并成 1 处按位判断、
`TicketPlanBuilder` 与 `Program.cs` 的澳超过滤各 1 处、`DailyReview` 的复盘说明 1 处。

**怎么证明没改变判断结果**：新增 `SignalTagTests`，用 5×7×4×2 = 280 组
（水位变化 × 必发占比 × 欧赔形态 × 联赛）跑真引擎，逐条断言

两者一一对应，则新判定 ⟺ 旧判定。这套断言是给重构期对照用的，以后改了文案措辞删掉对应镜像即可。

还匹配 `HitProbabilityService` 追加的「模型改看客胜 61%」。所以 `AwayPick` 在两个来源都置位，
只在大升分支置位会让长水降权漏掉模型改向的那批场次。

### G. 没有 T−60min 重算

现在只有 08:40 / 11:40 / 16:40 / 20:40 四个保存时点，都用**保存那一刻**的盘按终盘规则解释。
越临近开赛的信息越值钱，但现在 16:40 保存的票，到 20:00 开赛前发生的变化不会重算。

**已落地的实现（11-03 晚）**

新增作业 `refresh-near-kickoff`（cron `*/10 * * * *`，超时 30 分钟）：

1. `CountNearKickoffStaleAsync` 找出「开赛时间落在 T−85 ~ T−55 分钟之间、
   且 `DataAt` 早于「开赛前 60 分钟」」的场次。`DataAt` 是那版预测所依据的盘口采集时间。
2. 有这种场次才跑一次全量重算（`RecommendAllAndSaveAsync`，同时重出票面），否则记「没有需要重算的场次」。
3. 重算后 `DataAt` 被刷成当前时刻，同一场不会反复触发。

**顺带修掉一个会互相破坏的隐患**：`DeleteRecommendationsByBoardDateAsync` 原来是
`DELETE ... WHERE Board=@b AND RecDate=@rd`，会把当天**已经结算**的行一起删掉。
四个保存时点是白天，撞不上；加上每 10 分钟一次的临场重算之后，晚场重算会反复抹掉早场的赛果和命中记录。
现在只删 `ActualResult IS NULL` 的行。

### H. 精选 0 场却发 14 元票【已改 11-03 晚】

今天竞彩胜平负精选 0 场（SignalLevel 不够），但让球场次有 3 条，于是照样出了 14 元的票。
用户看到「今日推荐 0 场」和一张票，认知上冲突。

这是既有设计（`JcStakePlanAsync` 一直用 `hcpRows` 而非 `strong`），不是 bug，
但要不要在页面上明确区分「精选」和「凑得出来的票」，需要你定。

**已落地的实现**：新增 `RecommendationSelection.ForJcTicketLegs`，票腿从「所有有让球方向的场次」
收紧到「让球命中率 ≥ 55%」——与 `ToJcHandicapItem` 文案里那句「不到 55%，不标精选」对齐。
`SaveTicketAsync` 和 `JcStakePlanAsync` 两条路径同时改，页面在票面下显示
「只采纳命中率 ≥55% 的让球场次，已排除 N 场不达标的」。

实测（11-03 19:18）：让球清单 8 场，概率 46.7 / 51.2 / 57.8 / 43.7 / 61.1 / 40.9 / 39.2 / 39.5，
只有 2 场达标 → 票从原来的多腿串关变成 **2 串 1、2 元**，排除 6 场。

为什么不是「精选 0 场就不出票」：让球盘和胜平负是两个市场，胜平负信号弱不影响让球腿的独立性；
真正的问题是**旧代码把不足 55% 的腿也拿去买**，那才是拿低概率换注数。
