# AiFootBall 数据采集与分析系统 · 设计说明

版本 v1.0 ｜ 2026-10-28 ｜ .NET 8 + SQL Server 2025

> **现行说明以 [`开发文档总结.md`](./开发文档总结.md) 为准**（最近整理：2026-10-30）。本文保留采集与表结构细节；下面「不在本期范围」里若干项（赔率时序、推荐、登录、数字彩选号等）后续已落地，勿再按本节范围理解系统边界。

---

## 1. 目标与范围

面向「足彩 / 福利彩票 / 大乐透」的数据沉淀与分析底座，第一版解决三件事：

1. **可复现地采集**：把 pinble、500.com 的公开数据稳定抓下来，断网、重跑、重复执行都不产生脏数据。
2. **结构化的存储**：开奖号码与赛事信息拆分到明细表，支持任意维度聚合，而不是把 7 个号码塞进一个字符串了事。
3. **直接可用的分析**：频率、遗漏、和值、奇偶、连号、冷热等常用指标开箱即用，并提供 HTTP 接口与面板。

第一版原文写的「不在本期」：赔率时序采集、预测模型训练、用户与权限体系、实时推送——其中赔率轨迹 / 推荐 / 登录等已在后续迭代实现，详见开发文档总结。

                                │
                 ┌──────────────▼───────────────┐

分层职责：

| 项目 | 职责 | 关键点 |
|---|---|---|
| `AiFootBall.Core` | 领域模型、`ILotterySource` / `IMatchSource` / `IOddsSource` 接口、配置项 | 与存储、与站点无关，便于接第二个数据源 |
| `AiFootBall.Data` | 连接工厂、建库器、彩票/足球/赔率/日志仓储、指标计算 `LotteryMath` | SQL 脚本以嵌入资源随程序集发布，可一键建库 |

| `AiFootBall.Collector` | 命令行入口（手动采集、回补、单次触发作业） | 无状态，随时可跑 |
| `AiFootBall.Api` | 只读分析接口 + 单页面板 + 内嵌调度宿主 | 采集与分析解耦，调度可与 CLI 二选一 |

## 3. 数据源逆向结果

### 3.1 pinble 历史开奖页

- 地址形如 `https://www.pinble.com/nav/lottery/history/{固定段}/{彩种段}.html`，彩种段是站点混淆过的字符串，已固化在 `LotteryType.SourceUrl` 字段里，不硬编码在代码中。
- 页面 `tbody#tbody` 一次输出 **200 期**，通过 `select` 前端切换显示 10/20/…/200 期，**不存在服务端分页**；`?page=`、`?issue=` 等参数均无效（已验证）。
- 行结构：`td[0]=期号`、`td[1]=开奖日期`、`td[2]=号码区`。
- 号码区为 `div.qiu-item`，按 class 区分球色：`qiu-red`（前区/红球）、`qiu-lan`（后区/蓝球/特别号）、`qiu-ju`（数字型彩票的个位号，如福彩3D、排列三、七星彩、快乐8）。
- 结论：pinble 适合做「最近 200 期的日常增量」，不适合做全量历史回补。

### 3.2 datachart.500.com（全量回补）

- `https://datachart.500.com/{code}/history/newinc/history.php?start=07001&end=26999`
- 支持 `ssq`（3,520 期）、`dlt`（2,940 期）、`qlc`（3,003 期），其他彩种 404。
- 期号为 **5 位**（`yy` + 3 位序号，如 `26122`），入库统一补成 7 位标准期号 `2026122`。
- 两种版式：`dlt/ssq` 每球一格；`qlc` 把 8 个号码挤在一格里用空格分隔 —— 解析器用「整格号码数 == 红+蓝个数」自动判别，无需按彩种写死。
- 附带销售额、奖池、一/二等奖注数与奖金，正好补上 pinble 缺失的字段。

### 3.3 live.500.com（足球）

- 页面 GBK 编码，必须显式解码，否则中文队名全乱码。
- 两个入口互补：
  - `wanchang.php?e=yyyy-MM-dd`：当日**全部完场**（单日可达 1,400+ 场），有比分、半场比分，**无让球**；
  - `?e=yyyy-MM-dd`：当日**竞彩赛程**（10~20 场），有竞彩编号与**让球盘口 `span.sp_rq`**。
- 行结构：`tr[id=a{fid}]`，联赛链接 `/zuqiu-{sid}/`、球队链接 `/team/{id}/`、比分在 `div.pk` 的 `a.clt1`（主）/ `a.clt3`（客）。
- 同一 `fid` 会同时出现在两个入口，需要**字段级合并**：赛果取完场页，让球从竞彩页补齐（`MatchSource.Merge`）。
- 少量地方联赛（如重庆城市联赛）联赛单元格为空，属源数据缺失，统计时归入「未知」。

### 3.4 odds.500.com（欧赔 / 亚盘 / 大小球）

每场赛事对应 3 个页面，均为 GBK，结构同为「外层 `table#datatb` + 公司行 + 底部汇总行 `div#table_btm`」：

| 页面 | 地址 | 每行结构 |
|---|---|---|
| 百家欧指 | `/fenxi/ouzhi-{fid}.shtml` | `td[2]` 内嵌表两行 = **初盘 / 即时**（各 3 个赔率）；`td[4]` 返还率两行；`td[5]` 凯利指数两行 |
| 亚指对比 | `/fenxi/yazhi-{fid}.shtml` | `td[2]` = **即时盘**（主水 / 盘口 / 客水），`td[4]` = **初始盘**，`td[3]`、`td[5]` 为对应变化时间 |
| 大小对比 | `/fenxi/daxiao-{fid}.shtml` | 同亚盘，三元组为（大 / 盘口 / 小） |

关键细节：

- **盘口数值**在「盘口」单元格的 `ref` 属性里（如 `两球半` 对应 `ref="-2.500"`），比解析中文盘口名可靠；中文名仅作兜底（`平手/半球/一球/球半…` → 0/0.25/0.5/1/1.5 的映射表）。亚盘为**有符号**：负=主队让球；大小球取绝对值。
- **初盘与即时是同一行的两组数据**，所以一次请求就能拿到终盘，不需要「赛前多次采样」。
- 欧赔页首行是初盘、次行是即时——可由页面自带的「同赔」链接佐证（该功能按官方说明就是用**初盘**赔率去匹配历史）。
- 页面底部 `平均值 / 最高值 / 最低值` 行同样是「初盘表 + 即时表」，其中只有平均值入库（`CompanyId = 0`），最高/最低丢弃以减少噪音。
- 每家公司以 `tr[id={cid}]` 标识，`cid` 即 500 的公司编号，作为 `FbOdds.CompanyId` 的稳定键。

**反爬（TencentEdgeOne Bot 防护）**：突发请求后站点会返回约 988 字节的 JS 挑战页，要求写入两个 Cookie 后 1.2 秒重载。两个值都能从挑战页正文直接算出，因此无需浏览器：

```
__tst_status = e.WTKkN + e.bOYDu + e.wyeCN      // 三个随机整数之和（实测恒为定值）
EO_Bot_Ssid  = n() 里的加数                     // 每次请求随机
```

`BotGuard` 用正则取出这两个数值写入共享 `CookieContainer` 后重试；再叠加 `RequestThrottle`（全局最小间隔、429 自动降速、连续成功后回落）与 `OddsConcurrency` 并发控制。实测稳态约 **1.4 s / 请求**（1 场 = 3 请求 ≈ 4.3 s）。

## 4. 数据库设计

库名 `AiFootBall`，全部使用 `dbo` 架构，脚本幂等（`IF NOT EXISTS` + `MERGE`），可反复执行。

### 4.1 彩票域

**LotteryType（彩种字典）**

| 字段 | 类型 | 说明 |
|---|---|---|
| LotteryId | int PK | 自增 |
| Code | varchar(20) UK | `dlt/ssq/qlc/fc3d/kl8/pl3/pl5/qxc` |
| Name / Category | nvarchar | 名称、福彩/体彩 |
| RedCount / RedMax | tinyint | 前区个数与取值范围（数字型彩票 RedMax=9） |
| BlueCount / BlueMax | tinyint | 后区个数与范围，0 表示无 |
| DrawWeekdays | varchar(20) | 开奖日，1=周一 |
| SourceUrl | nvarchar(400) | pinble 抓取地址，**配置化而非硬编码** |

**LotteryDraw（开奖主表，一期一行）**

- 唯一键 `(LotteryId, Issue)` —— 幂等的基础。
- 冗余存储 `RedNumbers` / `BlueNumbers` CSV（便于直接展示），同时存 `RedSum`、`RedSpan`、`OddCount`、`BigCount` 四个派生指标，避免查询时反复计算。
- `SalesAmount`、`PoolAmount` 来自 500；`Source` 记录该期最终采用的源。
- 索引 `(LotteryId, DrawDate DESC)` 支撑「最近 N 期」查询。

**LotteryDrawNumber（号码明细，一球一行）**

- 主键 `(LotteryId, Issue, BallType, Seq)`，`BallType` 为 `R`/`B`。
- 为什么要拆明细：频率、遗漏、位置分布等统计在 SQL 层可直接 `GROUP BY Number`，不必解析 CSV；代价是一期多 5~20 行，10,463 期共 78,044 行，量级完全可接受。
- 外键级联删除，重导某期时先删后插。

**LotteryPrize（奖级）**：`(LotteryId, Issue, PrizeLevel)` 主键，存注数与单注奖金。

### 4.2 足球域

| 表 | 主键 | 说明 |
|---|---|---|
| FbLeague | LeagueId（500 的 sid） | 联赛名，冗余到 FbMatch.LeagueName 以兼容无链接赛事 |
| FbTeam | TeamId（500 的 team id） | 队名、所属联赛 |
| FbMatch | MatchId（500 的 fid） | 时间、主客队、比分、半场、状态、让球、胜平负/让球胜平负/总进球（入库时算好）；另含赔率采集标记 `OddsCheckedAt / OddsStatus / OddsCompanyCount` |
| FbOdds | (MatchId, CompanyId, OddsType, IsOpening) 唯一 | 统一赔率表：`OddsType` 区分 EU/AH/OU，`IsOpening` 区分初盘/终盘；欧赔存主平客+返还率+凯利，亚盘存 `Handicap/HomeWater/AwayWater`，大小球存 `TotalLine/OverWater/UnderWater` |

`FbMatch` 的派生字段在写入前计算，避免查询端重复实现规则：

```
ResultSpf      = 主胜 '3' / 平 '1' / 客胜 '0'
ResultHandicap = sign(HomeScore + Handicap - AwayScore)
TotalGoals     = HomeScore + AwayScore
```

### 4.3 运维表

`SyncLog(TaskName, Source, StartedAt, FinishedAt, Status, RowsAffected, Message)` —— 每次采集留痕，便于排查「某天数据为什么没进来」。

## 5. 采集流程与幂等策略

```
对每个彩种：
  1. pinble.FetchAsync()       → 最近 200 期（号码权威源）
  2. 500.FetchAsync()          → 全量历史（ssq/dlt/qlc，含销售额与奖池）
  3. 按期号分组：
       号码取 pinble 的那条；
       销售额/奖池/奖级取字段最全的那条；
  4. UpsertDrawsAsync(): 一期一个事务
       MERGE 主表 → DELETE 号码明细 → 批量 INSERT 号码 → MERGE 奖级
  5. 写 SyncLog
```

关键取舍：

- **每期一个事务**：单期失败不影响其他期，同时保证「主表 + 明细」不会出现半条记录。
- **号码明细全量重建**（DELETE + INSERT）而不是逐球比对：逻辑简单、天然幂等，成本可忽略。
- **字段级 ISNULL 合并**：`SalesAmount = ISNULL(@SalesAmount, t.SalesAmount)`，重复采集时不会用 NULL 覆盖已有值。
- **限速**：`RequestDelayMs` 默认 800ms，单日足球只有 2 个请求，彩票 8~11 个请求，对目标站点压力可控。

实测性能：大乐透 2,940 期入库约 29 秒（约 100 期/秒）；8 个彩种全量约 2 分钟；足球 7 天（3,906 场）约 40 秒。

## 6. 分析指标定义

`LotteryMath` 中实现，API 与后续的报表/模型共用同一套口径：

| 指标 | 定义 |
|---|---|
| 出现次数 `TotalCount` | 样本期内该号码被开出的次数 |
| 近 30 / 近 100 期次数 | 以最新一期为基准的近窗口计数，用于热度 |
| 当前遗漏 `CurrentOmission` | 距最近一次出现的期数差，0 表示最新一期刚开出 |
| 最大遗漏 `MaxOmission` | 历史最长连续未开出期数（含初始段与末尾段） |
| 平均间隔 `AvgInterval` | `(末次位置 - 首次位置) / (出现次数 - 1)`，反映理论回补节奏 |
| 和值 `RedSum` | 前区号码之和；`SumDistribution` 为其分布 |
| 跨度 `RedSpan` | 前区最大号 - 最小号 |
| 奇偶比 / 大小比 | 奇数（大于 `RedMax/2`）个数占比，形如 `3:2` |
| 连号率 | 前区排序后存在相邻差为 1 的期数占比 |
| 重号 | 与上一期前区号码的交集个数，取近 20 期序列与均值 |

足球侧：`HomeWins / Draws / AwayWins / AvgGoals / Over25Rate（总进球≥3）/ BothScoreRate（双方均进球）`，按联赛聚合并要求场次 ≥ 3 才输出，避免小样本噪声。

## 7.1 赔率采集流程

```
1. 选队：OddsRepository.GetMatchIdsForOddsAsync(from, to, onlyMissing, limit)
        onlyMissing=1 时过滤 OddsCheckedAt IS NULL 或 3 天前失败过的
2. 分批：每 OddsBatchSize(40) 场一批，批内用 SemaphoreSlim/Parallel 并发 OddsConcurrency(2)
3. 单场：FiveHundredOddsSource 依次取 ouzhi / yazhi / daxiao
        每次请求先过 RequestThrottle；遇 428/429 冷却重试；遇挑战页 BotGuard 求解后重试
4. 落库：SqlBulkCopy → #OddsStage → MERGE dbo.FbOdds（按 MatchId+CompanyId+OddsType+IsOpening 覆盖）
        同时写 #OddsMark → 更新 FbMatch.OddsCheckedAt / OddsStatus / OddsCompanyCount
5. 汇总：写 SyncLog(task='odds')
```

幂等性：`MERGE` 命中唯一键即更新，重复采集同一场只会刷新数值与 `CapturedAt`；中途失败重跑用 `--missing` 从断点继续。

## 7.2 定时调度

- `JobScheduler` 基于 NCrontab（5 段：分 时 日 月 周），每 20 秒扫描一次到期作业，**串行执行**避免多作业并发抢占同一站点。
- 运行记录写 `SyncLog(TaskName = 'job:{name}')`；启动时读最近一次运行时间推算 `Next`，若已过期则立即补跑一次，然后按当前时间重新排期。
- 两类宿主共用同一实现：`Collector scheduler`（前台常驻）与 API 内的 `SchedulerHostedService`。**两者不要同时开**，否则赔率作业会双份打向 odds.500.com。

## 8. 部署与运维

- 目标库：`192.168.41.128:1433`，`sa` 账号，SQL Server 2025。连接串在 `appsettings.json`，也可用 `AIFOOTBALL_CONN` 环境变量覆盖（优先级更高，便于容器化）。
- 本机 Windows 启用了应用程序控制策略，**生成的 `.exe` 直接被拦截**，必须 `dotnet AiFootBall.Collector.dll` 方式运行。
- 定时采集由内置 Cron 负责（见 7.2），无需外部任务计划：
  ```
  每日 21:45   lotto-daily        # 开奖日 20:30 后出号
  每日 08:10   football-daily     # 回补最近 3 天赛程赛果
  每 30 分钟   odds-upcoming      # 刷新未来 30 小时赛事赔率
  每日 03:20   odds-backfill      # 补齐历史缺失赔率（单次上限 1200 场）
  ```
- 建议对 `LotteryDraw`、`FbMatch`、`FbOdds` 做每日全量备份（数据量小，`BACKUP DATABASE` 秒级完成）。

## 9. 已知限制与后续演进

**限制**

1. pinble 单彩种仅 200 期：福彩3D、快乐8、排列三/五、七星彩当前为近 200 期样本，长期依赖每日增量累积。（500 站仅开放 ssq/dlt/qlc 历史接口）
2. 足球让球覆盖率低：只有进入竞彩列表的场次才有 `sp_rq`，其余场次 `Handicap` 为空——但**赔率侧已覆盖亚盘**，可用 `FbOdds(OddsType='AH')` 的初/终盘替代 `FbMatch.Handicap`。
3. 赔率采集受站点限流约束，全量回补 3,906 场约需 4~5 小时，需分批/多晚跑完；不支持高并发。
4. 欧赔只保留初盘与终盘两个快照，中间的过程变化（每次调赔的时间序列）需走需登录的 ajax 接口，当前未采集。

**演进路线**

| 优先级 | 事项 |
