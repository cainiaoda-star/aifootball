# 500.com 反爬处置与 token 自动续期

> 背景：2026-11-01 21:54 起必发断供、11-02 22:05 起欧赔断供。
> 根因：`odds.500.com` 从「纯 JS 挑战」升级为「JS 挑战 + 腾讯 EdgeOne 交互式人机验证」两级。
> 状态：2026-11-03 已实现**全自动续期**，无需人工介入。

## 一、两级机制

| 层级 | 特征 | 能否算法通过 |
|---|---|---|
| 一级：JS 挑战 | 约 987 字节，含 `__tst_status`；要写入 `__tst_status=<三个随机数之和>#` 和 `EO_Bot_Ssid=<加数>` | 能，`BotGuard.Solve()` 已实现 |
| 二级：人机验证 | 约 2 KB，含「正在验证连接安全性」；页面中央一个 330×70 的 iframe，左侧是「确认您是人」复选框 | 能，见下文「自动勾选」 |

### 关键更正：token 不是 30 天过期，是被请求量打掉

`EO-Bot-Captcha-Token` 票面参数 `ticket_timeout = 2592000`（30 天）只是**上限**，实际寿命由请求量决定：

- 实测 2026-11-02 23:38 取的 token，到 00:00 就失效，中间只有约 1,200 次请求
- 同一台机器、同一 IP，用浏览器重新取一个，立刻可用

所以「定时每 30 天续一次」的想法是错的，必须**按状态触发**。

## 二、自动续期（已上线）

### 触发链路

```
采集请求 → OddsHttp 识别到验证页 → StatVerify++
        → TokenHealthService（每 30 秒巡检）
        → 本轮拦截 ≥ 4 次？ → TokenRefresher.TryRefreshAsync()
        → 启动本机 Chrome → 自动勾选复选框 → 读出 Cookie 落盘
        → BotGuard.LoadPersisted() 热装载 → 下一轮采集自动恢复正常
```

设计要点：

| 决策 | 原因 |
|---|---|
| 按**拦截次数**触发，不按时间 | token 寿命取决于请求量：空闲时几小时不失效，回补时 20 分钟就可能被打掉 |
| 累计 3 次拦截（**跨巡检窗口累加**） | 关键细节见下：单次拦截会触发全站冷却，30 秒窗口内根本凑不到多次 |
| 两次续期间隔 ≥ 8 分钟，每小时 ≤ 4 次 | 防止连续弹窗、也防止把 IP 风险分拉满 |
| 回补遇到连续 6 次拦截**主动中止** | 否则每场白等冷却，还会把场次误标成「无数据」 |
| 成功后 `Browser.close` | 无人值守场景不能每次留一个 Chrome 窗口 |
| 失败时保留旧 token | 旧 token 可能仍可用（浏览器会话与 HTTP 会话是两条线） |

### 踩过的坑：阈值不能按「单窗口增量」算

第一版巡检逻辑是「30 秒内新增拦截 ≥ 4 次就续期」。实测完全不触发：

`OddsHttp` 命中验证页会 `Throttle.Cooldown(30)`，全站节流器被压到 **1 请求 / 30 秒**，
于是 30 秒窗口内最多只有 1 次拦截，阈值永远够不到，自愈形同虚设。

修正两处：

1. `TokenHealthService` 改为**跨窗口累计**（`pending += delta`），连续 10 分钟无新拦截才清零
2. 验证拦截的冷却从 30 秒降到 **10 秒**（否则「连续 6 次中止」要等 3 分钟才触发）

### 自愈实测（人为破坏 token）

```
00:38 把 secrets/500-cookie.txt 的 token 改成 INVALID-TEST-TOKEN
00:39 启动一轮采样
00:40:20  TokenRefresher 日志：开始续期（触发原因：verify-hits）
00:40:25  已装载 1 项 Cookie
00:43 采样作业完成：赔率 30 点 / 必发 28 场
```

**从失效到恢复约 2 分钟，全程无人工。**

### 自动勾选（关键突破）

新开的浏览器会话（Cookie 里没有有效 token）**必定**弹交互式验证。通过 CDP 模拟点击即可通过：

1. `Page.bringToFront` + `Emulation.setFocusEmulationEnabled` —— 窗口不在前台时鼠标事件可能不被渲染进程接收
2. 取 `iframe[src*="captcha"]` 的 `getBoundingClientRect()`
3. 在 `(x + 30, y + height/2)` 派发 `mousePressed` / `mouseReleased`
4. 约 3 秒后页面跳转，`EO-Bot-Captcha-Token` 落种

实测全新浏览器配置：**6 秒内自动通过**，全程无人工。

## 三、人工兜底（自动续期失效时）

先看日志里是否出现「超过每小时上限 4 次」或「脚本未产出新 token」——那说明是 IP 级封禁，续 token 无用，需要换网络或等风控解除。

需要手工确认时，直接跑脚本（可见浏览器）：

```bash
cd D:\AiFootBall
node _probe\harvest.mjs "https://odds.500.com/fenxi/ouzhi-1364148.shtml" "D:\AiFootBall\secrets\500-cookie.txt" 240
```

脚本行为：

1. 若 9222 端口已有调试实例则复用（不会把请求转给别的实例）
2. 遇到验证页自动点击复选框，每 6 秒一次、最多 8 次
3. 拿到 token 即写盘（含配套 `User-Agent`）并关闭浏览器
4. 超时返回退出码 2，截图存 `_probe/harvest_timeout.png`

**token 与 UA 绑定**：文件里的 `User-Agent` 必须与取 token 的浏览器一致，代码会自动用它覆盖默认 UA。换 UA 等于换指纹，token 立即失效。

## 五、当前的吞吐上限：429，不是验证

实测单页约 0.4–0.7 秒可得（不触发挑战时），但会周期性收到 `HTTP 429 Too Many Requests`（响应体 38 字节的 `checking...` 脚本）。

- `OddsHttp` 全站共享节流器：基础 900ms，最高 4000ms，429 时冷却 3 秒
- 实际稳定吞吐约 **7–10 场/分钟**（并发 2）
- 历史缺口约 11,800 场（完场无欧赔）→ 单个 IP 跑完需 **20–30 小时**

**不要为了提速把并发调大**：429 会更密，节流器会顶到 4000ms 上限，反而更慢。要真正提速只能加出口 IP（代理池），那是另一个量级的改造。

## 六、作业频率的坑

`water-sample` 原本 cron 是 `* * * * *`（每分钟），但单次要采 30 场、耗时约 4 分钟——它会**一直占着全站节流器**，把回补和轨迹采样一起拖慢。

2026-11-02 已改为 `*/10 * * * *`（每 10 分钟）。这个改动写在 `D:\AiFootBall\src\AiFootBall.Api\job-schedules.json`，重启后仍然生效。

同理 `jc-odds-sample`（每 2 分钟，每次 4 秒）影响不大，可以保留。

## 七、回补进度怎么看

```sql
-- 起点：2026-11-02 23:41（首次修复上线）
SELECT COUNT(*) AS 已检查场次 FROM dbo.FbMatch WHERE OddsCheckedAt >= '2026-11-02 23:41:00';
SELECT COUNT(*) AS 仍缺欧赔 FROM dbo.FbMatch WHERE Status = 3 AND ISNULL(OddsCompanyCount,0) = 0;
SELECT COUNT(*) AS 从未采过欧赔 FROM dbo.FbMatch WHERE OddsCheckedAt IS NULL;
SELECT COUNT(*) AS 今晚必发场次, MAX(CapturedAt) AS 最新 FROM dbo.FbExchange WHERE CapturedAt >= CAST(GETDATE() AS date);
```

`Status` 取值：`0` 未开赛 / `1` 进行中 / `2` 取消 / `3` 完场。

## 八、换机器/重装时的检查清单

1. `secrets/500-cookie.txt` 存在且第一行不是注释（`LoadPersisted` 会跳过 `#` 开头）
2. `_probe/harvest.mjs` 存在，`node -v` 可用，Chrome 装在 `C:\Program Files\Google\Chrome\Application\chrome.exe`
3. 启动日志出现「500.com 验证 Cookie 已装载 N 项」+「token 自动续期已就绪」
4. `curl /api/token/status` 里 `enabled=true`
5. 手动跑一次 `POST /api/token/refresh`，返回 `ok=true`
