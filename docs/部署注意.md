# 部署注意（2026-11-03 遇到的两个问题）

## 一、不要在 `D:\AiFootBall` 直接编译

今天在 `D:\AiFootBall` 里 `dotnet build`（含 `-t:Rebuild`）都成功，但产出的
`AiFootBall.Sources.dll` 起不来：

```
System.IO.FileLoadException: Could not load file or assembly
  'D:\AiFootBall\src\AiFootBall.Api\bin\Release\net8.0\AiFootBall.Sources.dll'.
  应用程序控制策略阻止了此文件 (0x800711C7)
```

同一份源码在 `E:\WB_Aicode\aifootball` 编译，把产物拷贝到 `D:`，**同样的路径、同样的目录，就能跑**。
所以不是路径或权限问题，是 D: 那次编译出来的文件本身有问题（DLL 大小一致，哈希不同）。

排查记录：
- 文件没被占用（可独占打开）、没有 Zone.Identifier 附加流、Defender 无拦截记录
- 换 `-t:Rebuild` 无效
- 同一台机器、同一个 .NET 运行时，E: 的产物可以启动

**结论：产物来源决定能不能加载，与部署位置无关。**

### 正确流程

```powershell
# 1. 在 E: 编译
cd E:\WB_Aicode\aifootball
dotnet build src\AiFootBall.Api\AiFootBall.Api.csproj -c Release

# 2. 源码同步到 D:（Data 项目把 ../../db/*.sql 作为嵌入资源，db 目录也要同步）
#    改到哪些文件就同步哪些，db\ 有新增脚本时别忘了

# 3. 产物整目录覆盖
$src = 'E:\WB_Aicode\aifootball\src\AiFootBall.Api\bin\Release\net8.0'
$dst = 'D:\AiFootBall\src\AiFootBall.Api\bin\Release\net8.0'
Copy-Item (Join-Path $src '*') $dst -Recurse -Force

# 4. 重启
& explorer.exe 'D:\AiFootBall\start.bat'
```

### 重启前必须先停进程

`stop.bat` 不一定干净，稳妥做法：

```powershell
Get-CimInstance Win32_Process -Filter "Name='dotnet.exe'" |
  Where-Object { $_.CommandLine -like '*AiFootBall*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force -Confirm:$false }
Start-Sleep -Seconds 3
```

**重启会掐断正在跑的回补**（HTTP 请求随进程结束）。要重启就挑回补结束之后，
或者接受「进度从队列当前位置继续」——回补按 `OddsCheckedAt` 排序取未采场次，不会漏也不会重采。

## 二、`start.bat` 启动会失败一次

`explorer.exe start.bat` 之后立刻请求健康检查经常连不上，等 8~20 秒才起来。
不要看到第一次失败就去重复启动，会起两个进程抢 5088。

判断方法：

```powershell
(Get-NetTCPConnection -LocalPort 5088 -State Listen -ErrorAction SilentlyContinue | Measure-Object).Count
```

返回 1 才算起来了。

## 三、`appsettings.json` 的 `Limit` 不热更新

`PUT /api/jobs/{name}` 只能改 `Cron` / `Enabled` / `Hours` / `RecheckMinutes`，
**改不了 `Limit`**。`Limit` 在进程启动时读入，改 `appsettings.json` 后需要重启才生效。

Cron 改动会写进 `job-schedules.json`，重启后仍然保留。

## 四、E: 与 D: 的关系

| 目录 | 角色 |
|---|---|
| `E:\WB_Aicode\aifootball` | 工作区，所有改动在这里做，编译也在这里 |
| `D:\AiFootBall` | 生产，只接收源码 + 产物，从这里起进程 |

2026-11-02 核对过 84 个源文件内容完全一致（只差换行符）。**只改 E: 不会生效**，
必须同步到 D: 并覆盖产物。

## 五、`start.bat` 里的中文会让 API 静默起不来（2026-11-03）

旧 `start.bat` 第一行 `chcp 65001`，但文件本身是 GBK。切换代码页后中文行被解析错乱，
日志里能看到 `'启动' is not recognized as an internal or external command`，
后面的 `start` 命令有时会被吃掉——表现就是 **OCR 窗口起来了、API 窗口没有，而且没有任何报错**。

处理：`start.bat` / `boot-api.bat` / `boot-ocr.bat` **全部只写 ASCII**，中文一律不要。
启动器拆成三个文件：

| 文件 | 作用 |
|---|---|
| `start.bat` | 只负责开两个最小化窗口，调用下面两个 |
| `boot-api.bat` | `cd` 到根目录、跑 dotnet、stdout/stderr 全部追加到 `_api_out.log` |
| `boot-ocr.bat` | `cd tools\ocr` 跑 `node ocr-server.js` |

`boot-api.bat` 用绝对路径调 `%ProgramFiles%\dotnet\dotnet.exe`，不依赖 PATH。
起没起来直接看 `D:\AiFootBall\_api_out.log`，日志首尾各有 `==== boot` / `==== exited with N` 标记。

## 六、后台作业的单次执行超时（2026-11-03）

`JobScheduler` 主循环是串行的：一次 `lock` 里把所有到期作业都标成 `Running=true`，
然后一个个 `await`。**任何一个作业挂住，后面排队的全部停在 `Running=true` 永远不被调度**。

当天实测：13:26 之后竞彩采样卡了 65 分钟，`/api/jobs` 上 `exchange`、`water-sample`、
`jc-odds-sample`、`settle-hourly`、`settle-purchases`、`recommend-evidence` 六个作业同时
`running=true`，手动触发全部返回「正在运行」，水位和必发断采一小时。

根因是采样作业内部串行发几十上百个请求（竞彩四类玩法 21 场 ≈ 84 次），
单请求 `HttpClient.Timeout` 60 秒，被 500 限流时累计能到一小时以上——不是某个请求挂死，
而是**大量慢请求叠加，没有整体耗时预算**。

现在加了两层：

1. **单作业超时**：`JobTimeouts` 按类型给上限（采样类 8~15 分钟，回补类 90 分钟），
   到点用 linked CTS 取消，记 `TIMEOUT` 状态并继续下一个作业。
2. **看门狗**：每轮（20 秒）扫描 `Running=true` 且已超过「超时 + 5 分钟」的作业，
   强制释放标志并记 `STUCK`，防止取消信号也传不进去的死锁。

`/api/jobs` 新增两个字段：`runningSeconds`（已跑多久）、`timeoutMinutes`（该作业的上限），
页面上看到 `runningSeconds` 接近 `timeoutMinutes` 就知道这条正在异常。
