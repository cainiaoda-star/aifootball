## 根因一：重算 DELETE 无差别删未结算行 → 已开赛/已完赛的注被删

`MilkPickRepository.SaveDayAsync` 原来是：
`DELETE FROM FbMilkPick WHERE PickDate=@d AND Hit IS NULL AND SettledAt IS NULL`
**不看开赛时间**。结算每小时才跑一次，重算更频繁 → 「重算先跑 → 注被删 → 结算再来找不到行」。
11-08 结果：8 注里 6 注被删，其中包括两注**命中的**。FbMilkPick 11-08 只剩町田两注（都未中）
→ 复盘页显示「0 中」→ 用户看到的就是「一个都没中」。空跑台账因每 10 分钟冻结才留证。

修：
1. DELETE 加 `AND MatchTime > DATEADD(minute, 5, SYSDATETIME())`——只重写**未开赛**的注。
   口径：**开赛 = 票已买，不可撤回、不可重写**；要改只能走告警撤注（Voided），不是 DELETE。
2. INSERT 改 `INSERT ... SELECT ... WHERE NOT EXISTS`（同日+场次+玩法+档位），
   否则被留下的已开赛行会和新插的重复一行。

## 根因二：进行中的比赛被误判「取消」（朗斯-马赛）

`SettleAsync` 取消判据原来是「开赛时间已过 + 比分 NULL + Status=2」。
**比赛进行中完全满足这三条**（开赛了、比分还没采到），而数据源在上下半场会把 Status 短暂刷成 2。
11-09 04:19 paper-settle 把正在踢的 朗斯-马赛（实际 1:2）写死成 `ActualScore='取消'` 终态，
永久退出结算队列 → 该注永远 open。
修：两处（`PaperTradeRepository` / `MilkPickRepository`）都收紧到 **开赛 150 分钟后**仍无比分才算取消，
与完场判据同一条时间线。已把朗斯行恢复为待结算并重结（未中）。

## 推荐页加「撤榜展示区」（用户 08:15 要求：下面开一栏，上面只放正在发榜的）

**结构**：主榜只渲染未撤的注（上面）；撤下的一律进榜单下方 `#milkVoidSec`（下面）。

**两类来源，语义必须分开写**：
- `voided`：临场高危告警主动撤注，有 `AlertReason`/`VoidedAt`。
- `replaced`：曾上榜、当前榜面已无它 —— 后续重算把这一档换掉/筛掉。
  **这类注在 FbMilkPick 里是整行 DELETE，只有 `FbPaperTrade` 每 10 分钟冻结才留痕**
  （11-08 曼联「胜平 @13.00」→「平平 @6.15」就是这么消失的，用户次日问「你到底推没推过」时系统答不出来）。
  故新接口 `GET /api/milk/voided?date=` 用台账做差集（`NOT EXISTS` 榜面），**不另建撤榜表**：
  差集天然自愈，注换回来就自动从撤榜区消失。

**顺带修的两个会导致撤榜区失效的隐患**：
1. `SaveDayAsync` 的 DELETE 加 `AND ISNULL(Voided,0)=0`。否则撤注行未开赛 → 被删 → 重建为未撤，
   十分钟后「复活」到主榜，撤榜区一闪就没。
2. `ApplyTurnAlertsToPicksAsync` 清红标时，`Voided=1` 的行**保留** `AlertSeverity/AlertReason`。
   否则告警一消失，撤注理由被清空，撤榜区只剩「未记录原因」——唯一凭证被自己删掉。
3. `/api/milk/picks` 过滤改为 `SettledAt is null || Voided`：撤注当天结算后仍要留在撤榜区，
   否则「撤得对不对」这批最该被检验的样本当天就查不到了。

**数据修正**：11-08 补录时把「已被换掉的胜平 @13.00」也插回了榜面，导致曼联 BQ 同场两注并存
（违反「同场只留一注」）。已删除 FbMilkPick 那一行，台账保留 → 现在它作为 `replaced` 出现在撤榜区，
带赛果 `4:4 未中`（印证换档换对了）。
**11-08 口径更正：8 注 1.294 → 7 注 2 中，回报 1.479**（胜平是历史版本，不该并列计一注）。

验证：`node --check` 通过；用 vm + stub 跑 `renderMilkBoard` / `milkVoidedHtml` 三场景
（有撤注 / 无撤注 / 全撤）全部通过；`/api/milk/voided?date=2026-11-08` 返回 1 行 replaced。

只有 `bd-spf-pick`（生成），**没有任何结算代码**。这张台账从 11-06 建表起就没结算过，
所谓「北单成功率」只能临时写 SQL 回算 —— 系统自己不知道。

**回算结果**（41 注已完赛 / 5 注待开赛）：24 中、命中 58.5%、回报 1.145
（steady 30 注 18 中 60.0%/1.143 均赔 1.89；reverse 11 注 6 中 54.5%/1.151 均赔 2.09）。
**但这个数字要连着三条一起看**：
1. 模型概率均值 51.9% ≈ 赔率隐含 52.9% → 北单「准」是因为它买的是**最可能的那一侧**，
   不是判断更准。理论期望 0.519×1.89≈0.98，实测 1.145 的 +16 点在 41 注样本里不到 1 个标准差。
2. 台账 `Odds` 是**推荐时点 SP**，与实购终版差 10~46%（场16 让胜 2.91→实购 4.25、
   场36 让负 2.07→3.74、场23 2.45→3.83），所以 ROI 只能看方向，不是账本。
3. 北单是串关玩法：单注 58.5% → 10 串 1 = 0.585^10 ≈ **0.47%**。

**已落地**：
- 新建 `BdSpfSettlement`（Core，纯函数）：净胜=主−客+让球数，>0/=/<0 → 3/1/0。
  SQL 里**不写 CASE**——`HomeScore` 是 tinyint，`HomeScore-AwayScore` 会报 8115 溢出；
  且口径要能被单测锁死。让球数用台账自己的 `Handicap`（bd 板），**不能用 FbMatch.Handicap**（竞彩盘）。
- `BdSpfPickRepository.SettleAsync(7)`：SELECT 未结算行 → C# 判 → 事务内逐条 UPDATE，幂等。
  完场判据沿用「比分齐全 && (Status=3 || 开赛过 150 分钟)」。
- `BdSpfPickRepository.GetRecordAsync(30)` + `GET /api/bd/spf-record`：分组结算数/命中/命中率/均赔/回报/待结算 + 逐注明细。
- 作业 `bd-spf-settle`（`10,40 * * * *`，只配 Api 的 appsettings，**部署脚本不拷 appsettings，必须手改 deploy-package 那份**），
  进 `_recommendLane`（纯库作业，避免被 water-sample 饿死）；Collector 侧补注入 `bdSpfRepo` 以便 `--once` 手动跑。
- 前端 `index.html` 北单区块上方加「北单战绩」表，含赔率口径警示。
- `BdSpfSettlementTests.cs` 21 条（含 5 场真实回归：阿尔杰什 2:1 受让1 让胜、克拉科夫 2:1 让-1 走盘把两侧都杀掉、
  阿劳 0:3 让-1 让负、罗森博格 4:1 让-2 是让胜不是让负、伊拉克利斯 1:2 受让2 输球赢盘）。

**验证**：部署后手动跑 → 「补判 41 注；近 30 天累计 41 注 24 中（58.5%），回报 1.145」，
与回算完全一致；再跑一次 → 补判 0 注（幂等）；抽查 6 场走盘/深盘全部判对。
**遗留**：① 赔率口径（推荐时点 SP）没有终版 SP 字段，要精确记账得另存；② 腰斩/取消场次永远停在待结算，无作废标记。

## 17:50 北单「无价注」事故修复（用户：今天休息，没竞彩，自由北单）

**当天局面核实**：竞彩今日 0 场新盘（`BettingCard` 里 `jc` 的 11 场是周日020~030，00:15~04:00 开赛，当天凌晨已踢完）。
稳胆依赖竞彩，故也是 0 注。北单「今日 43 场」是**今天 00:05~10:00 已踢完**的场次；真正的本期只有
`MatchTime > now` 的 **6 场**（11-10 01:50~04:05：罗甲博托沙尼 / 丹甲哈维德夫 / 挪超克里斯蒂安松 /
西乙拉斯帕尔马斯 / 西乙萨瓦德尔(让-1) / 葡甲托里什恩斯）。

**事故**：`bd-spf-pick` 16:41 那版出了 5 注，其中 **145 克里斯蒂安松 vs 瓦勒伦加（平手盘）让负 41.3%**
的 `Odds` / `HandicapOdds` **全是 NULL**——该场北单页面抓不到让球 SP。这注照样上了榜、照样写进台账。
后果三条：① 用户看到一张买不到价的票；② 台账空价行进结算分母不进分子；③ 串关算不出回报。
根因：`BdSpfPickService.BuildPick` 直接 `Odds = r.HandicapOdds`，全链路没有一处校验非空；
`ForJcHandicap` 里那句「水位未知保留——那是数据缺口不是低赔」被沿用到了北单，但**北单是串关**
（缺一腿整串作废），逻辑不能照抄竞彩单关。

**修法**：`BdSpfPickService.HasUsablePrice(pick) => pick.HandicapOdds is > 1m`，
在 `steady`/`reverse` 排序取前 10 **之前**过滤（这样剔掉后还能靠后面的注补满 10 注）。
`BdSpfPriceGateTests.cs` 10 条锁死：有价放行 / 无价拦 / 赔率≤1 等同无价 / 当日 5 注只留 4 注。

**验证**：860 条测试全过；部署后 `POST /api/bd/spf-picks?save=true` → **steady=4、reverse=0**，
台账 5 行变 4 行（`SaveDayAsync` 先 DELETE 未结算行再 INSERT，脏行自动消失）：
拉斯帕尔马斯 让胜 1.69(46.3%) / 博托沙尼 2.54(43.3%) / 哈维德夫 2.42(48.5%) / 托里什恩斯 2.20(45.1%)。
作业正常，健康 tick 16.9 秒。

**★ 这一期的真实成色（必须记，避免以后误读）**：6 场里 5 场是**平手盘**，唯一的让-1（萨瓦德尔）被
「深盘让平雷」踢出。平手盘的「让胜」= 主胜且不平，**平局走盘全输**，所以这 4 注实质是
「胜平负单选主胜」，不是让球价值。4 注概率 43.3~48.5%、SPF 主胜 1.89~2.13，全是均势局，
没有任何一边被明显错价。**别把「让球概率 46% × 北单 SP 2.42 = 1.11」当成 EV**——
概率来自竞彩盘/模型、赔率来自北单 SP，跨市场比的 EV 天然虚高（§19、§20 同款陷阱）。
