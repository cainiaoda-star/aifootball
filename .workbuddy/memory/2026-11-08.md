**现象**

### 00:19-00:21 换 IP + 换 cookie 双测试：**仍然全拦，两个方向都无效**

| 时刻 | 条件 | 结果 |
|---|---|---|
| 00:18:19 | 换 IP 后、旧 cookie（00:10:59） | 43 秒完成，5/5 `verify-required`（对比 22:40 那三次是 10 分钟 TIMEOUT） |
| 00:19:41 | 换 IP 后、新 cookie（00:19:03 装载） | 42 秒完成，5/5 `verify-required` |

**`verify-required` 的确切含义**（`OddsHttp.cs:98-102`）：`BotGuard.IsVerificationPage(html)` 命中，即**服务器返回的 HTML 本身就是人机验证页**，不是网络不通、不是 403、不是 token 过期字段。所以「换 IP 治 IP 限流」这个假设**被证伪**——IP 换了，回来的还是验证页。

**「TIMEOUT → 43 秒快速拒绝」这个变化说明什么**：出口链路确实变了（不再被挂起），但风控判定不变。**不是链路问题。**

**harvest.mjs 只落盘 3 项 cookie 的结构性缺陷**（`_probe/harvest.mjs:131-143`）：
- `Network.getAllCookies` 拿的是 500.com **全部** cookie，但 `if (tok)` 分支只写 `EO-Bot-Captcha-Token` / `EO_Bot_Ssid` / `__tst_status` 三项 —— **全是反爬标记，没有任何业务会话（无 PHPSESSID）**。
- 注释写的是「通过人机验证后的 Cookie」，但脚本 6 秒点一次验证框、最多 8 次，成功条件只是「存在名字含 captcha 的 cookie」——**挑战页本身就有这个 cookie**。所以「SAVED / 已装载 3 项」这个"成功"是假的，它可能从未真正过验证。

**当前结论（按可信度排序）**
1. 最可能：**请求频率触发风控封禁**（water-sample 10 分钟 + jc-odds-sample 2 分钟 + exchange 手动重试，同 IP 高频打 500）。22:05 前一切正常、22:40 起突封，符合"突发封禁"特征。
2. 次可能：`harvest` 抓的是挑战页 cookie，从未拿到有效会话 → 续期是空转。
3. 已排除：token 字段缺失/过期（`/api/token/status` 显示 00:19:03 装载成功，紧接着采集仍拦）。

**处置决定**：**停止一切重试**。每一次失败的 exchange 都在同一 IP 上再加一次风控分，越试越死。等冷却（通常 2-3 小时）。明早 07:00 首次试探，只跑 1 次 `--limit 3`；跑通即恢复自动采样，跑不通就按降级方案出榜并在榜上标注。

**关键前提（明早核对时先看这条）**：换 IP 是否生效取决于 PPPoE 拨号在哪台设备。
- 光猫桥接 + 路由拨号 → 重启路由器会重新 PPPoE，出口 IP 变；
- 光猫拨号 + 路由当 AP → **重启路由器不换 IP**，必须重启光猫或等运营商重拨。
- 若重启后仍 `verify-required`，说明是**账号级风控**，只能人工在浏览器过一次人机验证。

**验证方式**：`water-sample` 每 10 分钟自跑，恢复后 `SyncLog` 会出现新 SUCCESS、`FbExchange` 时间戳前移。恢复即自动补采，不需手动干预。
