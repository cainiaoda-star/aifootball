## 1. `source-option-gap`：按玩法域核对，不是硬套 54

### 1.1 域是什么（唯一一份实现：`src/AiFootBall.Core/Models/JcPlayDomain.cs`）

| 玩法 | 档数 | 域（代码清单） |
|---|---|---|
| `SPF` | 3 | `3 / 1 / 0` |
| `NSPF` | 3 | `3 / 1 / 0` |
| `BQ` | 9 | `3-3 3-1 3-0 / 1-3 1-1 1-0 / 0-3 0-1 0-0` |
| `JQ` | 8 | `0`…`7` |
| `BF` | 31 | 主胜 13（含 `胜其它`）+ 平 5（含 `平其它`）+ 客胜 13（含 `负其它`） |

引擎原来自己写了一份「31/9/8/3/3」（`SnapshotComplete`），现在改为调 `JcPlayDomain.Size`——
一处口径一种实现，避免下次改一处漏一处。

**为什么必须是代码清单而不是档数**：生产上半全场真出现过脏代码。近 90 天受注卡里 3 场带 `平/胜`、`平/负`、`平/平`：

```sql
-- 只读复现
WITH c AS (SELECT DISTINCT MatchId FROM dbo.BettingCard WHERE Board='jc' AND MatchId IS NOT NULL),
     k AS (SELECT h.MatchId, h.OptionCode, rn=ROW_NUMBER() OVER (PARTITION BY h.MatchId,h.OptionCode ORDER BY h.CapturedAt DESC)
           FROM dbo.FbJcOddsHistory h JOIN c ON c.MatchId=h.MatchId WHERE h.Odds>1 AND h.PlayType='BQ')
SELECT MatchId, OptionCode FROM k WHERE rn=1 AND OptionCode NOT IN
 (N'3-3',N'3-1',N'3-0',N'1-3',N'1-1',N'1-0',N'0-3',N'0-1',N'0-0');
-- 实测 1362502 / 1414210 / 1493662 各 1 行（`平/胜`/`平/负`/`平/平`）
```

按档数比的话，这 3 场是「10 档，齐了」；按代码比才知道第 10 档是脏的、真档一档不缺。

### 1.2 判据（`MilkSourceSlate.Verify`，新增 `source-option-gap`）

对**每一个源场次**（包括引擎拒绝的、包括一场都没算的），逐玩法取域内代码做差集：

- 缺任一档 → `source-option-gap`，Key 形如 `900000001|周日001|BF|缺 1/31|1:0`，`Expected=31 Actual=30`；
- **域外多出来的代码不阻断**（那是数据卫生问题，不是少覆盖），`missing-option` 也只看域内键。

三个细节都是刻意的：

1. **对所有源场次查，不只对算过的**。若只查算过的场次，一场被 `no-odds` 拒绝、源侧又只采到 4 个玩法时，
   这个拒绝永远无从反驳——那正是 1419319 的反面。
2. **`no-odds` 的豁免不因「源侧只有 4 个玩法」而成立**：源侧档数 51 ≠ 0 → `contradicted-rejection`，
   同时把该条拒绝记录的 `Accepted` 改回 `false`，否则落库的拒绝记录会带着「合法」标记，账面上与真没价分不清。
3. **未启售不提供任何豁免口子**。要判「这一玩法没启售」，必须有源侧落库的启售清单；当前库里没有这个字段
   （`BettingCard` 只有 `SpfHome/Draw/Away`，没有逐玩法启售位），所以「没采到赔率」一律按缺档处理。
   这条是按要求选的保守方向：宁可阻断一轮，也不让采集缺口静默变成「本来就没有」。
   **若要开这个口子，需要给采集侧加落库字段（表结构变更，另行报批）。**

### 1.3 实测：受注卡场次的档位分布（决定这条判据的现实代价）

近 90 天进过受注卡的 **162 场**，逐场逐玩法取每键最新：

| 玩法 | 观测档数 → 场数 |
|---|---|
| `BF` | 31 → 162 |
| `JQ` | 8 → 162 |
| `NSPF` | 3 → 162 |
| `BQ` | 9 → 159、10 → 3（多的是脏代码，域内仍 9） |
| `SPF` | 3 → **157**、缺玩法 → **5** |

即：**历史上有 5/162 场（约 3%）SPF 一档都没采到**。按新判据这些轮次会 `failed`、榜面停在上一成功轮。
这是设计要暴露的采集缺口，不是误报——但它意味着**部署后如果采集侧偶发漏 SPF，那一轮不会出榜**。
实施顺序上建议：部署后第一轮先看日志里有没有 `source-option-gap`；若有，先修采集（JC 采样 2 分钟一轮，通常一轮就补上）。

只读核对当前批（21 场）：

```sql
WITH cur AS (SELECT MatchId, MatchNo FROM dbo.BettingCard
             WHERE Board='jc' AND CapturedAt=(SELECT MAX(CapturedAt) FROM dbo.BettingCard WHERE Board='jc')
               AND MatchId IS NOT NULL),
     k AS (SELECT h.MatchId, h.PlayType, h.OptionCode,
                  rn=ROW_NUMBER() OVER (PARTITION BY h.MatchId,h.PlayType,h.OptionCode ORDER BY h.CapturedAt DESC)
           FROM dbo.FbJcOddsHistory h JOIN cur c ON c.MatchId=h.MatchId WHERE h.Odds>1)
SELECT c.MatchNo, Plays=COUNT(DISTINCT k.PlayType), Opts=COUNT(*) FROM cur c JOIN k ON k.MatchId=c.MatchId AND k.rn=1
GROUP BY c.MatchNo ORDER BY c.MatchNo;
-- 实测 21 场全部 Plays=5 / Opts=54
```

### 1.4 源清单必须完整保留引擎跳过的比赛

源清单来自 `GetJcSourceSnapshotAsync`（只读 `BettingCard` × `FbJcOddsHistory`），**不经过引擎**，
所以引擎在写凭证前 `continue` 掉的场次一定还在清单里；缺凭证又缺拒绝记录 → `missing-input`。
本次没有改动这条链路，只加了时间边界（下一节）。

## 2 `CapturedAt <= StartedAt`：按轮截止

### 2.1 改了什么

`BettingRepository.GetJcSourceSnapshotAsync(DateTime asOf, ct)`：两张表都加了时间边界。

```sql
-- 受注卡：取「截至 asOf 的当前批」，不再是全表 MAX
AND c.CapturedAt = (SELECT MAX(CapturedAt) FROM dbo.BettingCard
                    WHERE Board='jc' AND CapturedAt <= @asOf)

-- 赔率：每键最新采样也必须早于 asOf
WHERE MatchId IN @ids AND Odds > 1 AND CapturedAt <= @asOf
GROUP BY MatchId, PlayType, OptionCode
```

调用方 `RecommendationService.SaveMilkAsync` 传的 `asOf` 就是写进 `FbMilkRun.StartedAt` 的那个 `runAt`，
一一对应，没有第二个时间来源。

### 2.2 为什么 running 头 + 最新采样时刻不够

- `FbMilkRun.StartedAt` 只记录「这一轮什么时候开始」，它不参与任何查询过滤；
- `LastSampleAt` 是**查出来之后**算的最大值，查的时候不限上界，于是：
  - 下一轮（或事后补采）写进 `FbJcOddsHistory` 的新采样，会被上一轮重新查出来 → `LastSampleAt` 前移、
    `OptionKeys` 变多 → 「那一轮该有几档」被未来数据改写；
  - 11-14 事后回查能看到 11 场、10:58 的赔率，就是这个机理；它**不能**用来证明 08:40 那一轮。
- 加了边界之后，同一 `runAt` 重放得到同一份源清单（隔离库 ④-13 实测，见 §4）。

## 3 队名：梯队身份过滤（修 §2.2 的 2 条误配）

### 3.1 两道闸（`ScorelineModel.Resolve` 核心名那一步）

`CoreKey` 会把 `U21`/`RB` 这类 ASCII 标记一起抹掉，所以「核心名相等」本身**不能**当身份判据。
在核心名兜底上加两道闸，任一不成立就跳过这一步（继续走下面的全局子序列，仍要求唯一命中）：

1. **梯队标记必须相等**：`ReserveMark(query) == ReserveMark(candidate)`。
   查询名不带青年/后备/女足标记时，绝不接受梯队候选；查询名自己带标记时，也只认同一个标记（`U21 ≠ U19`）。
2. **候选多出来的 ASCII 记号必须被查询名覆盖**：`AsciiMarks(candidate) ⊆ AsciiMarks(query)`。
   方向很关键——查询名多出 `RB`（`大宫松鼠RB`）是赞助商后缀，允许；
   候选名多出 `U21`（`谢周三 → 谢周三U21`）是另一支队，拒绝。

第二条顺带把 `II`/`B`/`JFV` 这类**不在 `ReserveMarks` 名单里**的形态也挡住了：
库里确有 `拜仁慕尼黑女足II队`、`科隆II女足`、`JFV不来梅U19` 这类写法。

连「认得」都不成立，与样本量无关。
