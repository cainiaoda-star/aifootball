## 1. 源清单按轮冻结的证据

### 1.1 存放位置：`FbMilkSourceMatch`（本次唯一新建表，尚未建）

一行 = 本轮源侧的**一场**，结局二选一：`Outcome='computed'`（引擎算了）或 `'rejected'`（引擎拒了）。

| 列 | 含义 |
|---|---|
| `RunId` | 哪一轮（唯一键 `UX_FbMilkSource_Run(RunId, MatchId)`） |
| `SalesDate` | 受注日（口径 `SteadyPickRules.SalesDate(期号, 开赛, 当天)`） |
| `MatchId` / `MatchNo` / `LeagueName` / `HomeTeam` / `AwayTeam` / `MatchTime` | 该场身份 |
| `LastSampleAt` | **该场各档 `MAX(CapturedAt)`** —— 采样截止时刻 |
| `OptionCount` / `Plays` | 档数与各玩法档数，如 `BF=31,BQ=9,JQ=8,NSPF=3,SPF=3` |
| `Outcome` / `Reason` / `Evidence` / `Accepted` | 结局与拒绝证据 |

写入点：`MilkPickRepository.SaveSourceAsync`（`MilkPickRepository.cs:819`），按 `RunId` **先删后写**，
所以同一轮重跑不会留两份。

**为什么这能回答「08:40 那轮该有几场」，而事后回查历史表不能**：
源清单是按 `RunId` 落库的快照，只由当轮 `GetJcSourceSnapshotAsync` 决定；
而 `FbJcOddsHistory` 是持续累加的历史采样表，事后按时间反查得到的是「今天 11 点有多少场、几条采样」，
它不携带「08:40 那一刻是否受注、是否已开赛」的信息。**两者不能互证。**

因此对 08:40 那一轮：**永远无法补证**（该表当时不存在），本轮不声称能补。
能补的只有「为什么当时看不见」——见 §1.4 的拒绝记录口径。

### 1.2 采样截止时刻与受注时点

- **采样截止**：该轮 `FbMilkRun.StartedAt`（同一次 `SaveMilkAsync` 内**先写 running 头再查源**），
  逐场另有 `LastSampleAt` 兜底；`MilkSourceSlate.Verify` 用 `runAt − LastSampleAt > 30min` 报 `stale-sample`。
- **受注时点**：`JcSaleHours.Sellable(matchNo, matchTime, beijing)`（`RecommendationSelection.cs:52`）三条件：
  ① 期号属于当日 → ② 未开赛 → ③ 未过停售时点（一~五 21:58 / 六日 22:58，9:00 前不开）。
  这份实现**与打分入口 `ScoreAsync` 是同一份**（11-14 抽出来的），两处各写一遍就是漏改的入口。
- **采样新鲜度的边界**：`stale-sample` 只拦「引擎算了的场次」，不拦「从未采到样」的场次——
  后者由 `OptionCount=0` → 引擎报 `no-odds` → 源侧 `contradicted-rejection` 反向核（§1.4）。

### 1.3 拒绝记录（同一张表，`Outcome='rejected'`）

原因枚举 + 证据前缀，全部机器可核（`MilkSourceSlate.cs:120` 起）：

| Reason | 证据前缀 | 接受? | 条件 |
|---|---|---|---|
| `not-sale` | `sale=` | **否** | 无正当条件（出现即上游过滤与本轮不一致） |
| `league-excluded` | `list=` | 是 | 命中 `NoPickLeagues` / `NoParlayLeagues` |
| `no-odds` | `options=0` | 是 | 源侧档数必须确为 0，否则 `contradicted-rejection` |
| `name-missing` | `team=empty` | 是 | 主/客队名为空 |
| `name-unresolved` | `team=` | **否** | 须独立库检证明是 `new-team` 才升级放行 |
| `new-team` | `team=` | 是 | 库检近 18 个月样本 < 门槛 |
| `thin-sample` | `games=` | 是 | 认得队但本联赛样本不足 |
| `no-distribution` | `grid=` | 是 | 分布为空/质量 ≤0 |
| `model-not-ready` | `ready=false` | **否** | 整轮概率都不可用，发布等于用空榜覆盖上一轮 |

六道判据（`MilkSourceSlate.Verify`）：`missing-input`（源有、凭证与拒绝都没有 → **1419319 的形态**）、
`duplicate-input`、`unexpected-input`/`unexpected-rejection`、`rejected-rejection`、
`stale-sample`、`missing-option`、`contradicted-rejection`。

### 1.4 缺口（必须点明）：源侧**自己**缺档，目前查不出来

现在的比较方向是「源有 → 引擎有没有」：`missing-option` 只抓「源侧有这一档、输入凭证里没有」。
如果**源侧本身少了档**（例如 BF 只采到 25 档），预期与输入会一起少，**两边同时为「对」**——
这与 1419319 当初的病因是同一类（判据取自被测对象的一侧）。

- 实测档位域（今日在售场次，两条独立查询）：`3(SPF)+3(NSPF)+9(BQ)+8(JQ)+31(BF)=54`，逐场恒为 54。
- 最小补法（**未实施，待批准**）：`MilkSourceSlate` 增加一条 `source-option-gap`，
  按玩法域 `{SPF:3, NSPF:3, BQ:9, JQ:8, BF:31}` 比对 `Plays`，缺任一档即该轮 failed。
  约 10 行、纯函数、隔离库加 1 个场景即可验。
- 这条属于本轮「不扩大修改」的边界内**新增判据**，所以只报不写；是否并入本次部署请示下。

### 1.5 通过标准（不锁定「5 场计算」）

判据是**逐场完备**，不是场次数：

1. 源侧每一场，`computed` 与 `rejected` 恰有一个（两个都无 → `missing-input`；都有 → `duplicate-input`）；
2. 每条 `rejected` 的原因在枚举内、证据前缀相符、且规则允许（§1.3）；
3. 每个 `computed` 场次：采样 ≤30min，且源侧每一档都在输入凭证的档位清单里；
4. 任一条不成立 → 该轮 `failed`，**不发布**。

场次数（算了几场、拒了几场）只作为日志摘要，**不作为通过条件**。

### 1.6 供独立审查的只读 SQL

```sql
-- 某一轮的源清单（按轮冻结，唯一证据）
SELECT Outcome, COUNT(*) AS C, MIN(LastSampleAt) AS EarliestSample, MAX(LastSampleAt) AS LatestSample
FROM dbo.FbMilkSourceMatch WHERE RunId = @run GROUP BY Outcome;

-- 该轮每一场的结局与证据
SELECT MatchNo, HomeTeam, AwayTeam, OptionCount, Plays, Outcome, Reason, Evidence, Accepted, LastSampleAt
FROM dbo.FbMilkSourceMatch WHERE RunId = @run ORDER BY MatchNo;

-- 拒绝记录与源侧档数是否自相矛盾（no-odds 却源侧有档）
SELECT MatchId, MatchNo, Reason, Evidence, OptionCount, LastSampleAt
FROM dbo.FbMilkSourceMatch WHERE RunId = @run AND Reason = N'no-odds' AND OptionCount > 0;
```

## 2. 队名匹配的误配检查

### 2.1 实测规模（探针调 `ScorelineModel.Resolve`，竞彩近 90 天「联赛 × 队名」去重 **297** 组）

| 结局 | 组数 |
|---|---|
| 解析结果 = 竞彩原名 | 213 |
| 解析成另一个写法 | 76 |
| 认不出（null） | 8 |

76 条里绝大多数是**既有**的兜底（短名→长名子序列：拜仁→拜仁慕尼黑、马竞→马德里竞技、巴萨→巴塞罗那…），
与本次改动无关。本次新增的「核心名」兜底只在**查询名比库内名长或只差 ASCII** 时才生效。

### 2.2 ★ 新增规则实测的误配（**2 条，必须修**）

| 竞彩联赛 | 竞彩写法 | 命中库内写法 | 该写法 18 个月场次 | 判定 |
|---|---|---|---|---|
| 德甲 | 不来梅 | **JFV不来梅U19** | 1 | ★ 一队被认成 U19 |
| 英锦标赛 | 谢周三 | **谢周三U21** | 2 | ★ 一队被认成 U21 |

两条例子的机理相同：一级队样本不在 18 个月窗口里（或写法不同），而「B 队/U19/U21」的
`CoreKey`（去掉 ASCII 后）正好等于一级队的核心名，且该核心名在索引里**唯一** → 兜底命中梯队。

- 好消息：两条的样本都 < 出注门槛 5，会走 `thin-sample` 拒发，**不会出票**；
- 坏消息：`KnowsTeam` 为真、「认成了哪支队」是错的。若某梯队恰好 ≥5 场，就会拿梯队样本出票。
  `毕尔巴鄂` 这次解析到 `毕尔巴鄂竞技`（正确，因为西甲联赛内子序列先命中），说明风险取决于窗口内有没有一队样本，**不稳定**。
- 最小修法（**未实施，待批准**）：核心名兜底前加一道与子序列**同款**的过滤——
  `IsReserveOrYouth(cand) && !IsReserveOrYouth(query) → 跳过`（女足标记同理）。1~2 行，同函数内。
  既有 `MatchSubsequence` 本来就有这道过滤（`ScorelineModel.cs:448`），兜底这步漏了。

### 2.3 歧义组（返回 null，不猜队）——这条是可靠的

按核心名统计（全库 18 个月）：**1493 组**核心名撞 ≥2 个写法，全部返回 null。典型：

| 核心名 | 库内写法 | 说明 |
|---|---|---|
| 哥本哈根 | 哥本哈根 / B93哥本哈根 / U19 / U17 | 两支不同俱乐部，正确判歧义 |

| 法兰克福 | 法兰克福 / FSV法兰克福 / U19 / FC法兰克福 | 正确判歧义 |
| 女足 | AGF女足 / FHL女足 / HPS 女足 …（16 个） | 通用词，凑成一组，等价于「全不命中」 |
| 学院 | Pac学院 / FAD学院 / …（8 个） | 同上 |

结论：**「全库唯一」只保证不猜，不保证是对的**；错的那部分见 §2.2，只有梯队一种形态。

### 2.4 认不出的 8 组（明细）

## 3. 真实写入路径与发布边界

### 3.1 BF 全 31 档（含尾部档）实测

路径：`MilkPickEngine.BuildDetailed`（真实赔率 `FbJcOddsHistory` 每键最新 + 真实拟合模型 178,556 场）
→ `CollectSnapshots`。两场均在售、输入凭证 1 场、拒绝 0 条。

**周六008 罗达JC vs 福伦丹（荷乙）**：BF 31 档 = 28 常规 + 3 尾部，

| 玩法 | 档数 | Σ纯模型 | Σ混合 | Σ市场 |
|---|---|---|---|---|
| BF | 31 | **100.002** | **100.000** | 99.925 |
| BQ | 9 | 100.000 | 99.999 | 100.010 |
| JQ | 8 | 99.999 | 99.999 | 99.996 |
| NSPF | 3 | 100.000 | 99.999 | 100.067 |
| SPF | 3 | 100.001 | 100.000 | 100.026 |

尾部档：`胜其它 1.731/1.921`、`平其它 0.367/0.434`、`负其它 1.637/1.619`（纯模型/混合）；
最小档 `0:5 0.345`，最大档 `1:1 10.156`。

**周六005 布雷达 vs 埃门（荷乙）**：BF Σ纯模型 **99.998**、Σ混合 **99.999**、Σ市场 99.913；
尾部 `胜其它 3.480/3.557`、`平其它 0.461/0.465`、`负其它 1.326/1.165`。

混合公式实测反推：`w = (混合 − 纯模型) / (市场 − 纯模型)` 落在 **0.29~0.33**（设定值 0.3），
说明混合值确实按「(1−w)·模型 + w·市场」算，没有被市场单边支配。

> 注意 w 反推**不能**用来发现单位错：11-14 那批坏数据反推出来同样是 0.30
> （0.997→30.68 在 99.913 这条直线上）。单位错只有靠**三列各自合计 ≈100 且彼此同尺**才暴露——
> 当时纯模型合计 0.997、市场 99.913，比值 0.010（要求 0.9~1.1），这才是 `MilkProbScale` 该拦的点。

`MilkProbScale.Verify` 两场均为**通过（0 条）**。

> 下表第 2 行作废（`DROP TABLE` 会丢审计数据，且回滚的目的不是清库）。

| 场景 | 动作 |
|---|---|
| 部署后要回退到 `69aed2ce` | 只回退二进制 + 重启；旧代码不引用新表，`FbMilkSourceMatch` 留着**完全无害**（旧代码不读不写） |
| 是否清表 | **不清、不 `DROP TABLE`**。保留新表，避免回滚动到数据 |
| 回滚是否丢数据 | 不丢。新表只存源侧快照/拒绝记录，不存票、不存战绩、不参与结算 |

### 4.4 顺带说明：旧构建怎么处理这些 DDL

`69aed2ce` 里没有 `FbMilkSourceMatch` 相关语句，所以旧构建跑起来不会建它、也不会因它报错。
这也意味着：**若先部署后反悔，表留下来但没有写入方**，`read` 侧（旧代码）也看不见——
不会出现「半新半旧」导致榜面异常的情况。
