## 1. 上一轮错在哪

第十一轮把放行条件从「1 道闸」改成「2 道闸」：

```
场次 < 3（独立库检）  且  库内没有同一身份的相近写法   →   升级 new-team，Accepted=true
```

它解决的是「零计数被直接当成新队」，**没解决判据本身**：两道闸用的是同一种输入——
「用**这个名字**查到了多少」。而 `name-unresolved` 的成因本来就是**名字写法不同**，
所以这个输入天然回答不了「这支队是不是新的」。

- 「谢周三」按本名 0 场 / 「谢菲尔德星期三」74 场；
- 「不来梅」按本名 0 场 / 「云达不莱梅」58 场。

改成两道闸之后，只要恰好**没有登记过**另一种写法（探查抓不到改字、纯缩写），
`0 场 + 探查为空` 依然会放行 —— 等于「用计数证明身份」，换个包装而已。
这就是本轮要取消它的原因，也是第十一轮结论「零计数不能证明是新队」当时**没有真正落地**的地方。

## 2. 本轮唯一改动

**删除升级路径**，`name-unresolved`（含自报的 `new-team`）恒不接受。
两次独立查询保留，但**只用来写清拒绝理由**。

| 情形 | 旧判定（第十一轮） | 新判定（本轮） |
|---|---|---|
| 库检不可用（`-1`） | 拒绝 | 拒绝（`无法证明身份（独立库检不可用）`） |
| 场次 ≥ 门槛 3 | 拒绝（队名存疑） | 同（未动） |
| 场次 **0**，探查为空 | **升级 `new-team`、放行** | **拒绝** |
| 场次 **0**，探查没做 | 拒绝 | 拒绝（理由里写「变体探查未完成」） |
| 场次 **0**，查到相近写法 | 拒绝（相近写法） | 同（未动） |
| 场次 **1~2**（任何探查结果） | **升级 `new-team`、放行** | **拒绝**（`按本名只查到 N 场`） |

代码位置与具体行为（`src/AiFootBall.Core/Models/MilkSourceSlate.cs`）：

- `Verify` 的 `name-unresolved` 分支：删掉 `final.Add(new MilkInputRejection { Reason = ReasonNewTeam, Accepted = true })`
  这一整段（连同 `continue`）与其 `!probed / similar.Count==0` 两分支；
  现在三条出口**都**落到 `defect`（→ `rejected-rejection` → `Accepted=false`）。
- 拒绝文案按证据分层，便于事后判读：
  ```
  队名无法确认（按本名查得 0 场，门槛 3）
    ；库内没有同一身份的其它写法，但这不能证明该队是新的。
    解析失败时零计数与低计数都不能作为新队证明，本轮阻断，须补别名或人工确认
  ```
  查到相近写法时替换为「库内存在同一身份的相近写法（谢周三≈谢菲尔德星期三），属队名解析缺陷」；
  探查未完成时写「变体探查未完成（不足以说明任何一侧）」——**三种文案都不放行**。
- `ReasonNewTeam` 常量**保留但已停用**：只用于读懂库里/日志里的旧行，规则 `Accepted=false`；
  调用方自报按 `name-unresolved` 重走同一套判定。没有任何代码路径再产生它。
- `DefaultMinTeamGames` 仍 = `MilkThresholds.MinTeamGames` = **3（未改）**；
  它的作用从「可以放行」变成「只用来**加严**」（≥ 3 判队名存疑）。

`Sources/RecommendationService.cs`：把库检的对象从「只有 name-unresolved」扩到「name-unresolved + 自报 new-team」，
这样自报那一路也能拿到准确的库检场次（之前会命中「独立库检不可用」，理由失真但同样阻断）；
注释同步说明变体探查**只作诊断**。

## 3. 「已确认身份但样本不足」另行区分（门槛未动）

这是与 `name-unresolved` **不是同一件事**的一类，本轮只确认它没被误伤：

| 原因码 | 身份 | 条件 | 判定 |
|---|---|---|---|
| `thin-sample` | **已确认**（模型解析出了这支队） | 本联赛样本 < 3 | 规则内拒绝，`Accepted=true`，**不阻断发布** |
| `name-unresolved` | **未确认**（解析失败） | 任意场次 < 3 | 阻断（本轮）；须补别名或人工确认 |

两者门槛都是 3。区别只在「身份有没有被确认」，不在数字大小——
`ThinSample_SameLowCount_IsStillAccepted_BecauseIdentityIsConfirmed` 用**同样 2 场**的两条记录并排验证：
一条 `thin-sample` 通过、一条 `name-unresolved` 阻断。
