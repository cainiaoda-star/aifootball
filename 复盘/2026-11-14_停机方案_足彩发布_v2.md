## 0. 结论摘要

| 问题 | 核实结论 |
|---|---|
| `PUT enabled:false` | **只阻止新 due 入队**；不取消已 `Running`（含排队 / 在途）；不结束 SyncLog `RUNNING`；不保证 SQL 收尾 |

## 1. 代码依据（只读）

### 1.1 `enabled:false` 与排队

- 主循环 due 选取：`Job.Enabled && !Running && Now >= Next`（`JobScheduler.RunAsync`）。`Enabled=false` → 不再选入 due。
- 入队时立刻 `Running=true`，`QueuedAt=Now`，`RunningSince=null`；拿到 lane 后才写 `RunningSince`。
- `Update(..., enabled)` **只改** Enabled/cron/Next；**不** `Cancel` Pending、**不**清 Running。
- 面板：`runningSeconds` 仅在 `Running && RunningSince` 有值时计算 → **排队中 `running=true`、`runningSeconds=null`**。只盯秒数会漏排队。

### 1.2 看门狗 / STUCK

- HardLimit 到期：清 `Running`/`RunningSince`/`QueuedAt`，Cancel Pending，写 `STUCK`。
- `[hung]` 文案明确：**「可能仍在后台跑」** → 标志消失 ≠ 写库结束。
- `[queued]`：本次排队取消；若通道上已有其它作业，仍须等那些作业排空。

### 1.3 进程退出与计划任务

- `RunAsync` 在 `stoppingToken` 取消后：对 `detached` **最多等 15 秒**，超时注释为「收尾超时就算了」。
- 计划任务 `AiFootBall-API` → `boot-api.bat` → `dotnet …AiFootBall.Api…`。`Stop-ScheduledTask` 停的是任务实例；**不能当作已保证** ASP.NET 协作取消 + 在途 Upsert 原子收尾。
- 既有部署脚本路径含 `Stop-Process -Force`：**本方案禁止沿用**。
- 启动时 `SweepAbandonedAsync` 会把遗留 SyncLog `RUNNING` 标 `ABORTED`——说明「进程先死、库事务未确认」是已知破坏模式，应避免。

### 1.4 持久化面

- 面板改启用状态写入 **`job-schedules.json`**（`JobScheduleStore`），**不是** `jobs.json`。
- 本方案可改 schedules；**禁止**覆盖/改写 `jobs.json`；冻结包仍不含 `jobs.json`。

## 3. 恢复矩阵（成功 / 失败 / 放弃）

**原则：逐项恢复到快照 `enabled`；不得把原本 false 启成 true；不得「全部 true」。**

| 结局 | 何时触发 | 恢复动作 | 验收 |
|---|---|---|---|
| **A. 发布成功** | 新进程 health 达标且 §7 验收通过 | 对暂停清单中每一项：`PUT` 使 `enabled` **等于快照**（true→true，false→false）；cron/hours/recheck 与快照一致 | `GET /api/jobs` 与快照 enabled 逐项一致；`lotto-*` 仍为快照态（应为 true）；`odds-sample-late` 仍 false；`jobs.json` SHA 未变 |
| **B. 发布失败已回滚** | 拷贝/启动失败，已恢复 `010b1ad0` 备份并拉起 | **同 A**：按快照恢复 schedules 启用态（回滚 DLL **不会**自动还原 `job-schedules.json`） | 同 A + build=`010b1ad0` |
| **C. 窗口放弃（未停进程）** | 排空超时 / 出现 `[hung]` / 无法确认在途 | 进程仍在跑时：按快照 `PUT` 恢复启用；必要时用备份文件核对未误写 | 同 A；现网 build 不变 |
| **D. 已 Stop-ScheduledTask 但放弃发布** | 端口已下、未拷贝或拷贝未完成 | **先**按备份/`enabled-snapshot` 写回 `job-schedules.json`（或启动后立刻按快照 PUT）**再** `Start-ScheduledTask`；禁止带着全 false schedules 启动后不管 | 启动后 enabled 与快照一致 |

任一步骤中断：优先恢复作业启用态，再报告；**禁止**留下「采样全停、数字彩仍以为会跑」的静默失败。

## 4. 排空判据（须同时满足）

暂停 PUT 完成后开始计时；**全部**满足才允许进入停进程：

| # | 判据 | 如何查 | 不通过则 |
|---|---|---|---|
| D1 | 暂停清单内每项 **`running=false`** | `GET /api/jobs` | 等待；超时→放弃 |
| D2 | 同上 **`runningSeconds` 均为 null** | 同上（执行中才有秒数） | 同 D1 |
| D3 | **不得**仅用「秒数没了」判空：若曾见 `running=true` 且 `runningSeconds=null`，须等到该项 `running=false`（排队出清） | 同上 | 同 D1 |
| D4 | SyncLog **无** `Status='RUNNING' AND FinishedAt IS NULL` 且 `TaskName LIKE 'job:%'`（至少覆盖暂停清单对应 `job:{name}`） | 只读 SQL | 等待；超时→放弃 |
| D5 | **静默窗**：D1–D4 连续满足 **≥60s**（建议每 10–15s 复测） | 轮询 | 被打断则重新计静默 |
| D6 | 排空观察期内若出现新的 **`STUCK` + `[hung]`**（或 lastMessage 含该前缀） | `/api/jobs` 或 SyncLog | **立即放弃**（标志已不可信） |
| D7 | （可选加强）只读 `sys.dm_exec_requests`：无来自本 API 连接、长时间运行的写语句；若**无法可靠关联会话**，不得用「查不到」当通过，只作旁证 | SQL | 关联不了则依赖 D1–D6；有明显长事务→放弃 |

**明确不作为「已排空」的依据：**

- 仅 `runningSeconds` 消失或变为 null；  
- 仅 `lastStatus` 从 TIMEOUT/STUCK 变化；  
- HardLimit 触发后 Running 被清；  
- 健康检查 `stalled=false` / 端口仍通。

**排空硬截止：** 见 §6 时间表；到点未满足 → 走恢复矩阵 C，不进入停进程。
