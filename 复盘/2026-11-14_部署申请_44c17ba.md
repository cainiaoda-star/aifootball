### 3.2 唯一约束确认：`RunId + MatchId`

**不是纸面推断**——隔离库 `AiFootBall_AuditTest` 用的就是同一个 `new MilkPickRepository(auditStr)`（`MilkIsolatedCheck.cs:81`），即由**同一份** `EnsureRunSchemaAsync` 建出过这张表，实际结构如下：

| 索引/约束 | 类型 | 唯一 | 主键 | 唯一约束 | 列（按序） |
|---|---|---|---|---|---|
| `PK_FbMilkSourceMatch` | CLUSTERED | 是 | **是** | 否 | `Id` |
| `UX_FbMilkSource_Run` | NONCLUSTERED | **是** | 否 | **是** | `RunId`, `MatchId` |
| `IX_MilkSource_Run` | NONCLUSTERED | 否 | 否 | 否 | `RunId`, `SalesDate` |

**唯一性没有 NULL 逃逸**：SQL Server 的唯一约束视 NULL 为相等，若参与列可空就会出现「多行 NULL 也唯一」的漏洞。这里 `RunId nvarchar(40) NOT NULL`、`MatchId bigint NOT NULL`，两列都非空，所以「同一轮同一场只能一行」是硬约束。

**为什么是 (RunId, MatchId) 而不是 (SalesDate, MatchId)**：

- 四张表保留历史后，同一场会在多个轮次各留一行；键里必须含 `RunId`，否则第二轮写同一场就撞 2601（`FbMilkPick`/`FbMilkGate` 已经各踩过一次，见 `OPS-DATA-CHANGES.md` 11-13 19:04 行）。
- 一场只属于一个受注日，`SalesDate` 由 `MatchId` 决定，放进键里是冗余，还会掩盖「同一场被算到两个受注日」这类错误。

**写入语义**：`SaveSourceMatchesAsync` 在同一事务里先 `DELETE ... WHERE RunId=@run` 再 `INSERT`，所以重发同一轮是幂等的；唯一约束的实际作用是拦住「payload 里同一场出现两次」这种静默重复。

**索引冗余情况（如实披露）**：`UX_FbMilkSource_Run` 与 `IX_MilkSource_Run` 都以 `RunId` 为前导列，前者唯一、后者非唯一。后者是为「按 RunId + 受注日筛」准备的，不是必需但也不冲突；本次按代码原样建，不做额外优化。

### T3 采集停摆 —— 先证明「本应采样」，再判停摆

作业清单缺失或计划任务异常时，站点**看起来完全正常**（页面能开、日志不报，只是什么都不采）。但不能「10 分钟没看到新数据就判停摆」——休市、批次空档、上游本就无数据，都会让这个判据误报。所以分两步。

**第二步：判停摆**

- 阈值取 **max(8 分钟, 4 × 基线最大间隔)**；当前基线 120s，故为 8 分钟。
- 超过阈值仍无新 `CapturedAt` 越过部署时刻 → **停摆，回滚**。
- 若基线本身异常（该时段无采样，或最大间隔远大于 120s）→ **不判停摆**，按「本应采样」不成立处理：记录现状、报告，等我判断，不自行回滚。

> 这一条的意义：回滚本身要再停一次机。基线不正常时贸然回滚，等于在「本来就没在采」的时段里制造额外停机，还会掩盖真正原因（例如上游无数据）。

```sql
   AND s.Outcome = 'rejected' AND s.Reason = 'name-unresolved'
 ORDER BY inputRowsEver DESC, s.MatchNo;
```

**`inputRowsEver` 只是调查线索，两个方向都不能当判据：**

- **有历史输入 ≠ 真误伤**：那些行可能是**旧版错误匹配**的产物。第十轮之前 `ScorelineModel` 的核心名/子序列兜底确实会把梯队或近似名配成一线队，于是「算过」本身可能就是错的。拿它证明「现在挡住是回归」，等于把旧 bug 当基线。
- **无历史输入 ≠ 真新队**：1419319（大宫松鼠RB vs 山形山神）是被引擎在**写输入凭证之前**跳过的，库里 0 行，但它不是新队，是队名没解析出来。零计数既可能真新、也可能一直是缺陷。

**T6 的动作**：生成上面的清单，附每场的 `Reason`/`Evidence`，以及该 MatchId 历史输入行的 `VersionTag`（能看出是哪一版引擎算的）与当时的竞彩写法，**报告给我**，由我决定「回滚 / 放行 / 补别名后重跑」。我不自行处置，也不把「被挡」写成部署失败。

## 6. 旧榜识别方式

**为什么需要专门说明**：失败轮也会把注单写进 `FbMilkPick`（隔离库 ④-16d 已实测：E 轮 `Status='failed'`、`FbMilkRunDate` 0 行、但 `FbMilkPick` 真有 1 行）。所以看「库里有没有新数据」会把失败轮误认成已发布。

**榜面的选轮逻辑**（`PublishedRunSql`，逐字）：

```sql
DECLARE @run nvarchar(40) =
    (SELECT TOP 1 rd.RunId
       FROM dbo.FbMilkRunDate rd
       JOIN dbo.FbMilkRun r ON r.RunId = rd.RunId
      WHERE rd.SalesDate = @d AND r.Status = 'success'
      ORDER BY r.StartedAt DESC, rd.RunId DESC);
```

即：**只认「写进 `FbMilkRunDate` 且成功」的轮**，按 `StartedAt` 取最新。

**三步判定当前榜面是新是旧：**

| 步 | 查什么 | 结论 |
|---|---|---|
| ① | `FbMilkRunDate` 今日最新行的 `RunId` | 这就是榜面当前指向的轮 |
| ② | 该 `RunId` 在 `FbMilkRun` 的 `Status` | 必须 `success`；否则状态机失效（T5） |
| ③ | 该 `RunId` 的 `StartedAt` 是否晚于部署时刻 | 晚于 = 新榜跑过；早于 = **仍是旧榜**（11:40 那轮） |

**必须避开的三个错判：**

1. **不要看 `FbMilkPick` 有没有新行** —— 失败轮也写行；
2. **不要看 `FbMilkRun` 的最新行** —— 失败轮 `StartedAt` 更晚，`TOP 1 ORDER BY StartedAt` 会挑到失败的；
3. **不要看页面注数变化** —— 新批次本身就会改变注数。

**实际查询（照抄可用）：**

```sql
-- A. 今日榜面指向 + 该轮状态 + 是否在部署之后
SELECT TOP 1 rd.RunId, rd.PickCount, r.Status, r.StartedAt, r.PublishedAt
  FROM dbo.FbMilkRunDate rd JOIN dbo.FbMilkRun r ON r.RunId=rd.RunId
 WHERE rd.SalesDate=CAST(GETDATE() AS date)
 ORDER BY r.StartedAt DESC;

-- B. 今天所有轮次（含失败），看 16:40 到底有没有跑
SELECT RunId, Status, StartedAt, InputCount, SnapshotRows, GateRows, PickRows, FailReason
  FROM dbo.FbMilkRun
 WHERE RunDate=CAST(GETDATE() AS date)
 ORDER BY StartedAt DESC;

-- C. 失败轮是否写了注单（有行但不上榜 = 正常，不是异常）
SELECT RunId, COUNT(*) AS picks FROM dbo.FbMilkPick
 WHERE PickDate=CAST(GETDATE() AS date) GROUP BY RunId;
```

判读口径：

- B 里出现 16:40 的轮、`Status='success'`、A 里 `RunId` 也变成它 → **新榜已生效**；
- B 里有 16:40 的轮但 `Status='failed'`、A 仍指 `20261114T114017-9f2974` → **榜面是旧榜**，按 T6 判断是否回归；
- B 里根本没有 16:40 的轮 → 作业没跑（按 T3 方向排查），不是判据问题。
