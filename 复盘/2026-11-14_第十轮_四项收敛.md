## 1. 引擎与源账本：同一轮、同一截止时刻

**链路上只有一个时刻**（`RecommendationService.SaveMilkAsync`）：

```
var runAt = DateTime.Now;                                        // ① 轮次时间点
var build = await RecommendMilkWithGateAsync(jcRecs, ct, asOf: runAt);   // ② 引擎取价 ≤ runAt
run.StartedAt = runAt;                                           // ③ 写进 FbMilkRun
source = (await _repo.GetJcSourceSnapshotAsync(runAt, ct))...     // ④ 源快照 ≤ runAt
```

`JcOddsRepository.GetLatestAsync(ids, ct, asOf)` 的 SQL 用 `CapturedAt <= @until`（`asOf` 为 null 时取
`DateTime.MaxValue`，不写 `@asOf IS NULL OR`，避免为「不限」多付一次扫描）。不给 `asOf` 的调用
（API 预览、稳胆 `DailyFollow`、`ReviewOdds`、回测）保持旧行为——**它们不产台账、不做按轮核对**。

### 证据：截止后的新采样不改变本轮计算（隔离库 ④-14，新增）

同一个 `asOf` 取两次价，中间插一条 `asOf+8min` 的同档新价：

| 观测 | 结果 |
|---|---|
| 引擎输入档数 | 3 → 3（全 SPF） |
| 逐档（玩法\|档位\|赔率）摘要 | **完全相同** |
| 派生量：`SnapshotComplete` / `BlendNormalizer` | `True→True` / `1.042051→1.042051` |
| 不加边界再查一次 | `SPF\|3 = 1.550`（1.55，**证明那条新价确实落库了**） |

因为引擎的输入是这份取价结果的纯函数，输入逐档相同即结果相同；④-13/13b 只证明边界写对了，
④-14 才证明**边界之后的写入不会改本轮**。

## 2. 历史样本计数：与解析共用同一个身份函数

`TeamNames.SameIdentity(query, candidate)` 现在是**唯一一份**身份判据，两处调用：
`ScorelineModel.Resolve`（核心名兜底）与 `BettingRepository.GetRecentTeamGamesAsync`（独立库检计数）。
第九轮的两个函数（解析用「子集」、计数用「互相包含」）已删除。

**判据最终定为「梯队层次相同」**（`TeamNames.HierarchyMark`）：中文标记（青年队/后备队/预备队/二队/
B队/女足/女子）+ ASCII 年龄段 `U15~U23` + 罗马数字 `II/III/IV` + 单独的 `B`。

### 为什么不是「候选的 ASCII 记号 ⊆ 查询的记号」

先用子集方向实现后复跑 297 组，结果 **213 / 72 / 12**（原 213/74/10），多出两组认不出：

| 竞彩写法 | 库内写法 | 库内场次 | 原因 |
|---|---|---|---|
| 埃因霍温 | PSV埃因霍温 | 147 | 候选多 `PSV` |
| 辛那提 | FC辛辛那提 | 75 | 候选多 `FC` |

也就是说「多一个字母」不等于「另一支队」——`PSV`/`FC`/`RB`/`SC` 是俱乐部名的一部分。
机器可辨的真正差别是**层次**：`U18`/`II`/`B` 才是另一支队。改成层次判据后：

- 297 组回到 **213 / 74 / 10**，与第九轮逐项相同；A1 表（74 条命中另一写法）里 **没有一条 ★ 误配**；
- 反而比上一轮多挡住两类别写法：`BKMA` / `BKMA II`、`帕丘卡` / `帕丘卡III`（`II`/`III` 不在中文名单里）；
- `曼联` / `曼联U18`（`U18` 原来不在名单里，库里 U15~U23 全有）、`马拉加` / `马拉加 B`、`FC摩城` / `FC摩城二队` 同样挡住。

### 子序列链路不再「捡回」被核心名拒绝的候选

发现的真分叉：`帕丘卡` 在核心名那步被身份闸拒绝后，**子序列那步又把它捡成 `帕丘卡III`**。
现在 `MatchSubsequence` 对**同核心名**的候选加同一条身份判定；冲突时升级为**歧义**而不是跳过——
`米兰` 同时对上 `国际米兰`（核心名不同）与 `AC米兰`（核心名相同），跳过 AC 会得到
「唯一命中 = 国际米兰」，把歧义悄悄变成错误答案（回归测试 `AmbiguousShortName_IsRejected` 正好抓到这个）。

### 计数口径的实际变化（159 组）

旧口径把 B 队/青年队并进一线队：本菲卡 234→86、尤文 269→164、塞尔塔 64→0。
10 组「认不出」里**只有 `谢周三` 跨门槛（31→0）**——旧 31 场全来自 `谢周三U21`，
一线队在库内叫 `谢菲尔德星期三`（74 场）。后果是它会被判「真新队」放行，**这是判据变弱**。
正解是同义名（`谢周三 → 谢菲尔德星期三`），属队名归一化，未擅自加入，**列待批准**。

## 4. 玩法域用于完整性、归一化、计算入口

`JcPlayDomain` 成为唯一清单（SPF/NSPF 3、BQ 9、JQ 8、BF 31），新增
`Contains(playType, code)` 与 `Normalize(code)`（`胜其他` ≡ `胜其它`）。四处改用它：

| 位置 | 改动 | 挡住的形态 |
|---|---|---|
| 完整性 `SnapshotComplete` | 从「数档数 ≥ 31」改成「每一档都存在」 | 一条脏码顶替一条合法档，档数仍是 31 |
| 归一化 `BlendNormalizer` / `ObservedOverRound` | Σ1/赔率 只算域内档位 | 脏码进分母 → **所有合法档混合概率被整体压低** |
| 计算入口 候选生成 | `bfPoints`、JQ、BQ 逐档过滤 | 脏码被当成一档去算概率 |
| 全档存档 `CollectSnapshots` | BF/JQ/BQ 逐档过滤 | 存档多出永远对不上的行 |
| 预期侧 `MilkExpectedSlate.Domains` | 全部委托 `JcPlayDomain`（原来 BF「不设域」） | 预期要求存档、实际不存（假缺档） |

### 一个必须记下来的事故（本轮自查抓到）

第一版只用 `Contains(playType, code)` 过滤、**没保留玩法相等**，结果 SPF 的 `0/1/3` 被算进 JQ 的分母
（JQ 的域恰好是 `0..7`）：探针实测罗达JC **ΣBlended 100 → 40.745**，而三列都「有值」、没有任何一处报错。
已补回 `PlayType == playType`，并加单测 `BlendNormalizer_DoesNotLeakOtherPlaysSharingOptionCodes`。

### 脏码不变性（单测 `CollectSnapshots_DirtyCodeLeavesLegitProbabilitiesUntouched`）

走真实写库路径 `CollectSnapshots`，BQ 9 档分别在「无脏码」与「多两条 `平/胜`/`平/负` @2.0」下各跑一次：

- 存档行数相同，且**不含** `平/胜`/`平/负`；
- 每一合法档的 `ModelPctPure` / `MarketPct` / `BlendedPct` **逐项相等**；
- 整组 ΣBlended 仍在 100±0.5。
