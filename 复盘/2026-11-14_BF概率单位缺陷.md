# BF 概率存档单位缺陷（2026-11-14）

> 状态：**缺陷已定位并修复代码，生产数据未做任何标记或回填**（等另行报批）。
> 结论先行：11-14 那 4 轮产生的 620 行 BF 存档，`ModelPctPure` 列写的是 0~1 的小数，
> 而同表另外四个玩法写的是百分数。**这批 BF 存档不可用于任何评估**。

## 1. 现象

`FbMilkProbSnapshot` 按场按玩法合计三列（11-14 08:40 轮）：

| 场次 | 玩法 | ModelPctPure | BlendedPct | MarketPct |
|---|---|---|---|---|
| 1416115 | **BF** | **0.997** | **30.680** | 99.913 |
| 1416115 | BQ | 99.999 | 99.999 | 100.014 |
| 1416115 | JQ | 100.001 | 100.001 | 100.057 |
| 1416115 | NSPF | 100.000 | 100.000 | 99.992 |
| 1416115 | SPF | 100.000 | 100.001 | 100.045 |

四个玩法都是 100，只有 BF 是 1 和 30.68。混合值是 `(1−w)·模型 + w·市场`，
模型项小了 100 倍，市场项正常 → 混合值被市场支配，于是落在 30.68 而不是 100。

## 2. 根因

`MilkPickEngine.CollectSnapshots` 的 BF 分支写的是 `Math.Round(bfPure[code], 3)`，
而 `bfPure` 里存的是 **0~1 比例**（候选段的 `Blended()` 也吃比例，所以上游不能改）。
同一方法的其他四个分支都写了 `× 100m`。**一行漏了换算，且没有任何校验会发现它。**

单元测试 `AuditSnapshotTests.CollectSnapshots_CoversEveryOption_NotJustPicks` 当时
喂的是 `30m`（把比例当成了百分数），所以测试跟着错误一起通过——
这正是「判据与被测对象同源」的翻版：测试数据里的单位约定和生产代码里的不一致，但没人对过。

## 3. 影响范围（只读统计）

| 项 | 值 |
|---|---|
| 行数 | 620 行（31 档 × 5 场 × 4 轮） |
| 轮次 | 4（`...064013-00ba49` / `...065013-298d45` / `...070013-162381` / `...084014-565820`） |
| 场次 | 5 场（1416115 / 1416117 / 1416124 / 1416128 + 1 场） |
| 日期 | **仅 2026-11-14**（BF 存档是 11-12 才加的分支，此前没有 BF 行） |
| 判据 | 按 (RunId, MatchId) 合计 `ModelPctPure < 2` 的组 = 20/20，全部命中 |

**不受影响的部分（已核对）**：

- **出票**：BF 候选用的是 `bfPure` 比例 + `Blended()` 比例，与存档列无关；
  本轮 2 注注单的 `ModelPctPure`（`FbMilkPick` 列）来自 `p.ModelPctPure`，是百分数，正常。
- **其他四个玩法**：合计 99.999~100.001，单位正确。
- **战绩/命中率**：只读 `FbMilkPick`，不读这张表。
- **11-13 及更早**：没有 BF 存档行。

## 4. 处置

### 4.1 已做（代码，未部署）

1. `CollectSnapshots` BF 分支补 `× 100m`，并在注释里写清「bfPure 是比例、表里的列是百分数」。
2. 新增 `MilkProbScale`：**发布前**按 (场次, 玩法) 校验
   - 三列合计必须接近 100（容差 1.0pp，实测其余四玩法落在 ±0.001）；
   - 三列彼此同尺（纯模型合计 ÷ 市场合计 必须在 0.9~1.1）。
   任一不成立 → 该轮判 failed、**不发布**。这条不是为了修当前这个 bug，
   是因为同类错误（某档用 0~1、某档用 0~100）不会让任何东西报错，只能靠合计兜住。
3. 修正了那条把比例当百分数的单元测试，并补 `MilkProbScaleTests`（6 个用例）。

### 4.2 未做（需另行报批）

- **未在库里给这 620 行打标记**（不加列、不改值、不删行）。
- **未回填**：不打算用「乘 100」重算历史行——那会把一个「当时的错」改成「看起来对」，
  而当时的混合值（30.68）是**错的语义**，重算成 100 也只是把错误藏起来。
- 因此本轮及以前的 BF 存档**不得用于**：
  - Hit@1 / Hit@3 的 BF 评估；
  - 任何按玩法分层的权重调整（`MarketWeightFor` 的 BF 权重 0.3）；
  - 「模型 vs 市场」对照表里的 BF 一行。

### 4.3 可机器识别的口径（供后续标记使用）

```sql
-- 受影响行：按 (RunId, MatchId) 合计 < 2 的 BF 组
WITH b AS (
  SELECT RunId, SnapshotDate, MatchId, SUM(ModelPctPure) AS s
  FROM dbo.FbMilkProbSnapshot
  WHERE PlayType = 'BF'
  GROUP BY RunId, SnapshotDate, MatchId
)
SELECT * FROM b WHERE s < 2;   -- 2026-11-14 实测 20 组 / 620 行
```

修好之后的判据是「合计 ≈ 100」，所以这段 SQL 天然只命中修复前的数据，
不需要额外的时间戳字段来判断「哪一批是坏的」。

## 5. 复验

### 5.1 单元（1132 通过 / 0 失败）

- `MilkProbScaleTests` 6 条：BF 小数当百分数、单玩法坏不影响其他玩法、
  五玩法各自合计（SPF / NSPF / BQ / JQ / BF）、尾部比分档（`3:x`/`x:3` 以上）单档也能判、
  合计只在整组有值时判（算不出某档不误判成单位错）。
- `AuditSnapshotTests`：`bfPure` 输入由 `30m/5m` 改为 `0.30m/0.05m`，断言落 `30.000m`——
  这条断言现在是「比例进、百分数出」，与生产同向，不再帮倒忙。

### 5.2 隔离库（`milk-isolated-check`，21 项全通过）

`④-8` 用真实缺陷形态喂进去（`ModelPctPure=0.079`、`MarketPct=14.2`），
实测**两条判据同时报出**：`prob-not-normalized`（合计 13.079 ≠ 100）+ `unit-mismatch`
（纯模型合计/市场合计 = 0.0056，不在 0.9~1.1）。任一成立即该轮 failed、不发布。

第一版这里判「不通过」的用例自己没通过：`unit-mismatch` 当时要求
「至少 2 档都有两列值」才比对，而 BF 组常常只有 1 档有值 → 漏判。改成 `>= 1` 后复跑全绿。
**这个 bug 值得记一笔**：判据自身写得太窄，会让「本来能抓到的错」静默通过。

其余与发布闸相关的场景：

| 场景 | 断言 |
|---|---|
| ④-1 | 完整轮发布后榜面指本轮 |
| ④-2 | failed 轮不覆盖上一成功榜面 |
| ④-3 | partial 轮不覆盖上一成功榜面 |
| ④-4 | 源 2 场 / 输入 2 场 → 源侧账本通过 |
| ④-5 | 缺一场输入（无拒绝记录）→ `missing-input` 不通过 |
| ④-6 | 6 档存档逐键对齐 → 通过 |
| ④-7 | 缺一档存档 → `missing` 不通过 |
| ④-8 | BF 小数当百分数 → 不通过 |
| ④-9 | 零注但有输入 → 照样发布（`PickCount=0`）且输入 2 行／存档 6 档／源侧 2 行齐全 |
