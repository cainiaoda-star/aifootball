# 输入覆盖缺陷：1419319（周六002 大宫松鼠RB vs 山形山神）整场消失

> 状态：**只读定位 + 代码修复，未部署、未改任何生产数据**。
> 结论先行：这场不是「被规则剔除」，是**队名解析在三级兜底里全部落空**，
> 引擎在读赔率之后、写输入凭证之前 `continue` 掉了它——而当时的核对口径
> 「预期 = 引擎自己写的输入凭证」，两边同时为 0，所以核对照样通过。

## 1. 现象

11-14 08:40 轮（`...084014-565820`），`RawMatches=6`（源侧 6 场受注）：

| 表 | 该场行数 |
|---|---|
| `FbMilkInput` | 0 |
| `FbMilkProbSnapshot` | 0 |
| `FbMilkGate` | 0 |
| 榜面 | 无此场 |

同轮另外 5 场正常。**「少了 1 场」这件事在库里没有任何痕迹**——
`funnel.Skipped` 只在内存里、最多 20 条、不落库，进程结束就没了。

## 2. 代码路径（逐跳定位）

`MilkPickEngine.BuildDetailed` 的 `foreach (var r in recs)`：

```
① NoPickLeagues.IsExcluded        → 未命中（日职乙不在名单）
② NoParlayLeagues.IsExcluded      → 未命中
③ r.MatchId is not long           → 有 MatchId，通过
④ odds.TryGetValue(mid)           → 有赔率，通过（funnel.WithOdds++）
⑤ 队名为空                        → 两队都有名，通过（funnel.Named++）
⑥ scores.ResolveLeague(...)       → 无别名，回原名「日职乙」
⑦ MarketDirection(points)         → 正常
⑧ scores.KnowsTeam(lg, 主/客)     → ✗ 主队「大宫松鼠RB」**认不出**
   → showRows 标 unknown-team，continue      ← 就是这里
```

关键点：第 ⑧ 步的 `continue` 发生在**所有落库动作之前**。
所以「引擎自己跳过一场」与「源侧本来就只有 5 场」在数据上完全同形。

## 3. 根因：`MatchSubsequence` 只允许查询名更短

`ScorelineModel.Resolve` 的兜底链是：别名表 → 本联赛精确 → 本联赛子序列 →
全局子序列。查「大宫松鼠RB」时：

- 别名表：没有 `大宫松鼠RB`
- 本联赛精确：库内写法是「大宫松鼠」，不等
- 本联赛子序列 / 全局子序列 → 都进 `MatchSubsequence(shortName, candidates)`：

```csharp
foreach (var cand in candidates)
{
    if (cand.Length <= shortName.Length) continue;      // ← 命门
    if (cand.Length - shortName.Length > 4) continue;
    ...
}
```

这行的语义是「查询名必须比库内名**短**」，因为子序列本来是为
「查询给短名（波兹南）、库内有长名（波兹南莱赫）」设计的。
而竞彩这次的写法反过来：库内「大宫松鼠」(4 字)，查询「大宫松鼠RB」(6 字)，
`cand.Length(4) <= shortName.Length(6)` → **每一个候选都被这一行跳过**，
三级兜底全空，`KnowsTeam` 返回 false。

同一行还有一个副作用：长度差上限 4 字（`cand.Length - shortName.Length > 4`）
在这类冠名后缀上也不成立——方向就是错的。

### 3.1 为什么之前没被发现

`ScorelineModel.Resolve` 的成功与否只看「能不能认出来」，识别不出来时
**没有任何计数、告警或落库**。而当时的发布前核对：
预期来自 `MilkInputMatch`（引擎自己写的凭证），
凭证里没有这一场 → 预期里也没有 → 差额为 0 → 判通过。
这是「判据取自被测对象的输出」第二次触发（第一次是 `input>0 且 snapshot>0`）。

## 4. 修复

### 4.1 队名解析（治根）

1. `TeamNames.CoreKey(name)`：去掉 ASCII 字母数字与 `·・.-_` 空白后的核心名。
2. `ScorelineModel._globalCore`：全库核心名索引，`BuildCoreIndex` 里
   **同一核心名撞两支以上直接记空串（=歧义）**，不做任何猜测。
3. `Resolve` 在全局子序列之前插一步：核心名**一字不差**且全库唯一才算命中。
   有歧义返 null——**宁可丢场，不猜错队**。
4. `TeamAliases` 补 `["大宫松鼠RB"] = "大宫松鼠"`（人工确认，可审计，
   不依赖自动推断；核心名兜底是防「下一个 `XX FC` 又没别名」）。
5. `GetRecentTeamGamesAsync` 按核心名归并计数（`months=18`），
   这样「主队叫大宫松鼠RB、客队侧叫大宫松鼠」两种写法共享同一答案，
   不会因写法不同被判「客队查不到」。

修复后实测（`team-check 大宫松鼠RB 山形山神 日职乙`）：

```
大宫松鼠RB → 大宫松鼠 | 联赛内 40 场 | 全库 64 场 | 认得：是
λ 主 1.820 / 客 1.193
```

### 4.2 场次级拒绝记录（治「看不见」）

`MilkPickEngine` 新增 `void Reject(rec, reason, evidence)`，把
**每一个写凭证之前 `continue` 的分支**都申报一条带证据的记录：

| 原因 | 证据前缀 | 是否接受 |
|---|---|---|
| `not-sale` | `sale=` | 否（恒不接受，说明上游过滤与本轮不一致） |
| `league-excluded` | `list=` | 是（须写明命中哪张名单） |
| `no-odds` | `options=0` | 是（源侧档数须确为 0，见 §4.3 的 contradicted 检查） |
| `name-missing` | `team=empty` | 是 |
| `name-unresolved` | `team=` | **默认否**，须独立库检证明是真新队才升级为 `new-team` |
| `thin-sample` | `games=` | 是 |
| `no-distribution` | `grid=` | 是 |
| `model-not-ready` | `ready=false` | 否（不该用空榜覆盖上一轮） |

规则与既有的档位级豁免同一套：「引擎自行跳过」不会因为改了个名字就变合法。

### 4.3 源侧快照（换判据基准）

新增 `BettingRepository.GetJcSourceSnapshotAsync()`：
`BettingCard` 当前批 × `JcSaleHours.Sellable`（**与 `ScoreAsync` 同一份实现**，
抽成 `RecommendationSelection.JcSaleHours.Sellable` 一处，避免两边各写一套受注判断）
× `FbJcOddsHistory`（同 `GetLatestAsync` 口径：`Odds>1`、每键 `MAX(CapturedAt)`）。

`MilkSourceSlate.Verify` 六道判据，每条都能机器核验：

| Kind | 含义 |
|---|---|
| `missing-input` | 源侧有这场，既无凭证也无拒绝记录（**1419319 的形态**） |
| `duplicate-input` | 凭证与拒绝记录同时存在 |
| `unexpected-input` / `unexpected-rejection` | 引擎处理了源里没有的场次 |
| `rejected-rejection` | 拒绝记录的原因不在枚举内 / 缺证据 / 证据前缀不符 / 该原因不接受 |
| `stale-sample` | 算过的场次最新采样超龄（> 30 分钟）——历史赔率有记录 ≠ 本轮仍有效 |
| `missing-option` | 源侧有这一档，输入凭证里没有——档位层面的少算 |
| `contradicted-rejection` | 引擎报 `no-odds`，源侧却有 N 档：两个源不能同时为真 |

`name-unresolved` 的独立判定：查该队近 18 个月完赛场次，
`>= 门槛(5)` 就判「队名归一化缺陷、不是新队」→ 不接受；
`< 门槛` 才升级成 `new-team`，并把 `dbGames` 写进证据。
库检不可用（返回 -1）时一律不接受——宁可少发一轮。

> 这里踩过一个顺序坑：`name-unresolved` 本身是 `Accepted=false`，
> 若先看 `Defect`，会直接拿到「不接受」的说明、永远走不到库检分支。
> 入口必须是 `r.EvidenceOk`（证据格式成立），不是 `Defect.Length == 0`。
