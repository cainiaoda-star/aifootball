## A. cards 通道隔离

### 现状
`LaneOf` 只把 `RecommendJobTypes` 分到推荐通道、`DetachedJobTypes`（仅 `jc-odds-sample`）分到竞彩通道，其余全部进 `_mainLane`（`JobScheduler.cs:545-548`、`:687-690`、`:701-`）。`cards` 因此与 exchange / water-sample / exchange-late / inplay 共用一条串行线。

### 改法
1. 新增 `private readonly SemaphoreSlim _cardsLane = new(1, 1);`
2. `LaneOf` 增加一档：`job.Type == "cards" ? _cardsLane : ...`（放在最前，避免被判成主通道）。
3. 不变超时（30 分钟），不变 cron，不变 `DetachedJobTypes`。

### 依据
- 实测耗时 3 秒、3 个 GET（`cards-daily` 三次分别 106/115/110 场，均 3 秒）。
- 同窗口 `exchange` 一次占用 900 秒，`cards` 排队 15 分 57 秒。
- 它排在主通道里没有任何收益：主通道串行的理由是「同打 500 接口会被限流」，而 cards 只 3 个页面。

### 风险（必须写明）
- **独立后与 500 采样并发**：`cards` 与 water-sample / odds-sample 同时打 500，共享 `OddsHttp` 的 900ms 节流与 429 惩罚。3 个请求的增量很小，但**这是并发量的净增加**，需要在隔离库压一次「三通道同时跑」观察 `Stat429/StatChallenge` 增量，不能只靠推理。
- **独立通道不等于顺序保证**。这正是你指出的点：通道隔离只是让它不再被挤，**不保证**它在 16:40 之前跑完（比如它自己挂了 40 秒）。所以**必须有 C**，不能只上 A。

### 回滚
删掉那一行分支即可，无数据影响。

## B. 手动采集留痕

### 现状
`POST /api/recommend/collect`（`Program.cs:1195-1199`）直接调 `CollectCardsAsync`，**不写 SyncLog、不写进程日志**。页面上有按钮直连这个口（`wwwroot/index.html:1090-1091`）。15:25:15 那批因此不可归因。

### 改法
1. 端点内包一层：执行前 `BeginAsync("cards:manual", "api", now)`，结束后 `CompleteAsync(status, rows, "jc x / bd y / sfc z")`——与 `job:cards-daily` 同一张表、同一套字段，只是 `TaskName` 不同。
2. 状态沿用 D 的三态（`SUCCESS` / `[no-sale]` / `FAILED`），不新造状态词。
3. 返回值加 `logId`，便于页面/排查时直接定位。

### 为什么放 `cards:manual` 而不是 `job:cards-daily`
两者语义不同：一个是「按 cron 采」，一个是「有人手点」。混在一条 TaskName 下，C 的「本轮成功」判据会被手动点击污染（手点一次就能让闸以为本轮采过了）。

### 注意
- 手动路径**不参与** C 的「本轮」判定（C 只认 `job:cards-daily` 的时段内成功），但**参与**「批次与最近一次成功采集是否配对」的校验（否则手点也会让库里的批次对不上任何记录）。
- 不新增表、不新增列。

## C. 出榜前批次时效闸（核心）

### 为什么必须有它
A 只解决「不被挤」，不解决「挤了也照发」。你指出的「独立通道 + 提前 10 分钟不保证先采卡后出榜」成立：cron 的时点差是**计划**，通道排队、重试、5xx 都会打破它。因此判据必须落在**事实**上：本轮采卡是否成功完成、库里批次是否就是它写的那一批。

### C1 判据、C2 判定表 → 已并入 **§K**（唯一口径）

本节的判据细节不再在此重复，避免两处口径（本项目已因"同一口径写两份"踩过）。这里只保留一句结论：

> 闸只问一个问题：**本轮出榜用的这批场次，是不是"本轮采卡成功"写进去的。**
> 本版**不设降级例外**（`DegradeEnabled=false`）：不是就拒绝，没有"旧批再顶一次"。唯一允许的"0 场"是 K2b 的 `no-sale`——它有独立的证据链，且不读旧批。

- 三层判据、同一条记录约束、有序判定表（10 个 verdict）、四档动作、显式关闭开关：**§K1–K4**
- `no-sale` 怎么证明、怎么出榜：**§K2b**
- 今天 16:40 那轮会被判成什么：**§K4 末段**
- 放置点与落痕：**C3 / §K5**

变量定义（与 §K2 同口径）：`runAt` = 本轮出榜的取数时刻（现有 `asOf` 口径，`GetJcSourceSnapshotAsync(runAt)` 同刻）。

### C3 落痕（零 schema 变更）

复用 `FbMilkRun` 已有字段：`Note nvarchar(400)`、`FailReason nvarchar(300)`、`Status`。不新增列。verdict 词表是 §K2 那 10 个，此表只定"写哪里"。

| 档 | `Status` | `Note` | `FailReason` | `FbMilkRunDate` |
| --- | --- | --- | --- | --- |
| 绿 `fresh` | `success` | 空 | 空 | 写 |
| 绿 `no-sale` | `success` | `no-sale-jc` | 空 | 写（空榜） |

### C4 放置点（一份实现，一个入口，三个调用者）

- 判定函数只有一份：`MilkBatchGate.CheckAsync(runAt)`，返回 verdict + 证据串（输入清单见 §K2）。
- 唯一入口：`RecommendAllAndSaveAsync`（`RecommendationService.cs:542`）**最前**，在第一个 `DeleteRecommendationsByBoardDateAsync` 之前。
- 该入口的调用者有三个，全部自动受保护，**不需要为任何一个开例外**：
  1. cron `save-recommendations`（含 `POST /api/recommend/save`）；
  2. `RefreshNearKickoffAsync`（`RecommendationService.cs:645`，内部直接调 `RecommendAllAndSaveAsync`）；
  3. `RunTurnGuardAsync` 的高危重算（`RecommendationService.cs:681`，同样调它）。
- **对上一版的更正**：原文写"两个调用点、refresh 传 `requireSlot=null`"，是错的——`refresh-near-kickoff` 与 turn-guard 都回到同一入口，给它传 null 等于给 10 分钟一次的作业开后门，旧批可以每 10 分钟合法重写榜面一次。已删掉这个例外。
- 闸拒绝时入口返回结构化 verdict，调用者据此记 `RowsAffected=0` + 原因，**不得写成成功**（否则 §D 修好的"失败当成功"在这里复发）。
- 与既有 `MilkRun.Partial/Skipped` 是**同一族语义**，不要另起一套状态词。

### 风险
- 「拒绝出榜」会让页面临时显示上一轮，需要页面能说清原因（`FailReason` 已有展示位）。
- **拒绝不会让榜变新**：榜面内容仍是上一轮（可能基于更旧的批次）算出来的。拒绝唯一的收益是"不让更旧的覆盖"，所以必须配告警；否则只是把"静默发旧批"换成"静默不刷新"。
- 若 cards 长期失败，会连续拒绝 4 轮 → 期望行为，但需要页面级提示：连续 2 轮红即置顶横幅（沿用现有告警位，不新造）。

## D. 采集空结果的明确状态

### 现状
- `GetGbkAsync` 拿到 `(html, reason)` 后**丢弃 reason**（`BettingCardSource.cs:682-687`）。
- `FetchJcAsync` 在 `html is null` 时返回空列表（`BettingCardSource.cs:23-27`）。
- `case "cards"` **无条件 Ok**（`JobScheduler.cs:1062-1072`）。
- `UpsertCardsAsync` 空列表直接 `return 0`（`BettingRepository.cs:208-211`）。

结果：反爬失败、页面改版、真无在售，三者都是 `SUCCESS + RowsAffected=0`。

### D1 三态（不做「一律失败」）
`OddsHttp.GetAsync` 已经给出完整原因词表：`http429`、`http428`、`http<code>`、`short<N>`、`empty<N>`、`challenge`、`verify-required`，成功时 `chrome` 或空。所以 `html is null` **天然就等于**「有原因的取数失败」，不需要新造机制。

| 状态 | 判据 | 采集侧 Status | 出榜侧 |
| --- | --- | --- | --- |
| `Ok` | `html` 非空且解析出 >0 行 | `SUCCESS` | 正常 |
| `NoSale` | `html` 非空、**页面结构标记存在**、但解析出 0 行 | `SUCCESS` + `RowsAffected=0` + message 前缀 `[no-sale]` | 允许出空榜（C 的 `no-sale` 分支） |
| `FetchFailed` | `html is null`（带 reason）**或** 页面结构标记不存在 | `FAILED` + 前缀 `[fetch-failed]` + 逐块 reason | 红 `jc-fetch-failed`（无降级） |

### D2 关键约束：0 行 ≠ NoSale
「解析出 0 行」必须再看一眼**页面结构标记**（受注表格容器是否存在）：
- 容器在、行数为 0 → 才有资格判 `NoSale`；
- 容器不在 → 视为解析失败（很可能就是挑战页/改版），**不得**判 `NoSale`。

这条是防止「站点改版 → 0 行 → 系统以为今天没比赛 → 出空榜 → 静默不发票」的唯一挡板。你要求「空结果不能一律判失败」，反过来也成立：**空结果同样不能一律判正常**。

### D3 前缀沿用既有约定
`[queued]` / `[hung]` 已是 ASCII 前缀、专供 SQL 筛选（`JobScheduler.cs:385-387`）。新增 `[no-sale]` / `[fetch-failed]` / `[partial]` 沿用同一约定，`Status` 列（varchar(10)）不动，避免动表。

### D4 返回类型
`FetchJcAsync/FetchBdAsync/FetchSfcAsync` 改为返回 `(records, status, evidence)`；`CollectCardsAsync` 汇总三态。`case "cards"` 按「三块全失败 → FAILED；含失败 → SUCCESS+`[partial]`；全 NoSale → SUCCESS+`[no-sale]`」映射。
**注意**：`[partial]` 与 C 的 `partial`（完整性）是两件事 —— 前者是「板块级取数不全」，后者是「单期场次覆盖不全」。两者都不得当成 `no-sale`。

### 结论：不建议缩短
1. **900 秒不是正常耗时，是最坏占用**。正常成功稳定在 318–328 秒，3 天三份样本一致；900 秒有 2.7 倍余量。缩短到 600 秒对正常轮仍安全，但——
2. **缩短不减少占用总量**。今天 6 次全部**恰好跑满 900 秒**（不是「差一点跑完」），说明每次都卡死到放弃。缩短只会让它更早放弃、然后按 20/30 分钟 cron 更频繁地重新进通道，**总占用未必下降，失败次数一定上升**。
3. **根因未查明**。今天 12:30 起才连续超时，上午 8 次全部 327 秒成功（`05:42` 之前是必发 token 失效导致的 FAILED，`08:21` 起恢复）。同一份代码同一时段，行为在 12:30 突变——这不是「超时设小了」，是有东西在下午变了（限流累计、cookie 半失效、或与 inplay 争抢）。**在查明前调数字是掩盖症状。**
4. **本轮拥堵已由 A 解掉**：cards 不再排在它后面，它跑多久都不影响出榜前的场次刷新（其余影响由 C 兜底）。

### 若后续仍 ≥3 次/日持续超过 14 天，再单独评估
评估时需要两条证据，缺一不可：①每次超时前的最后一条进度日志（现在没有，`exchange` 只记总耗时）；②区分「需要更长时间」与「卡住」——目前 900 秒的 6 次全是 `RowsAffected=0`，属卡住，不属需要时间。

## J. 问题陈述：两种策略不能靠「容差」混用（**已由 §K 统一，本节保留为问题记录**）

提出时间：2026-11-14 17:12（用户）。17:33 用户要求统一 → 结论见 **§K**，本节不再作为待决项。

原 C2 把下面两件事塞进同一个「容差」数字，是设计缺陷。它们的判据、语义、失败后果都不同：

| | **S1 本轮必须采到** | **S2 陈旧批次可放行** |
| --- | --- | --- |
| 判据 | 存在一条 `slot ≤ FinishedAt ≤ runAt` 的 `job:cards-daily` 成功记录 | 只要求 `cap` 距 `runAt` 在阈值内 |

| 今天 16:40 是否成立 | **不成立**（16:30 无成功记录，最近一次成功是 11:31:17） | 成立（65 分钟） |
| 失败后果 | 拒绝出榜，榜面停在上一轮 | 照常出榜 + `Note` 标注 |

**必须先选一条，再谈阈值**（↓ 17:33 已收敛为 §K4 的单一参数，下面三条仅留档）：

- **情形①只做 S1**：不设 `stale-bounded` 分支，配对容差 ±120 秒之外一律拒绝，`FailReason='no-capture-this-slot'`。代价是 cards 一旦失败就断榜，需要「连续 2 轮拒绝」告警兜底。

- **情形③两档并存**：需额外定义「何时允许降级」的触发条件（谁来判、判什么），且两条判据**各自独立落痕**——一个数字不能同时表达两件事。

**补充事实（供取舍）**：即使 A 上线，S1 也可能因 cards 自身失败而不成立（今天它 16:30 到期、16:46:12 才成功，是排队；但反爬/改版会让它彻底失败）。所以选①意味着一部分日子里确实会「当天不刷新榜」；选②意味着接受「榜可能基于几十分钟前的场次表」，只是必须写明。

**本节结论已并入 §K**：分层之后"必须本轮成功"与"例外额度"分开，二者不再冲突；17:41 用户选定 **情形①（只做 S1）**，即 §K 的 `DegradeEnabled=false`。`stale-bounded`/`stale-beyond`/`degraded`/`expired` 这批旧名全部作废，正式口径只看 §K2 那 10 个 verdict。

## K. 统一规则（17:33 起，17:41 按"降级关闭"定稿）：一个有序判定、四档结论、显式开关

### K1 分三层，且 L1 与 L2 必须落在**同一条**记录上

| 层 | 回答的问题 | 判据（三条都针对**同一条** `rec`） | 不成立 |
| --- | --- | --- | --- |
| **L1 时间一致性** | 库里这批，是不是 `rec` 这次采集写的 | `|cap − rec.FinishedAt| ≤ 120s` | 红 `batch-mismatch` |
| **L2 本轮达标** | `rec` 是不是本轮该采的那次，且真的成功 | `rec.Kind = job:cards-daily` 且 `rec.FinishedAt ∈ [slot, runAt]` 且 jc 板块成功 | 红 `no-capture-this-slot`（降级已关闭） |

**★ 禁止"某条记录配对、另一条记录本轮成功"。** `cap` 必须与**同一条** `rec` 的时间对得上，而这条 `rec` 也必须是满足 L2 的那一条。两条各自成立不算通过——那是用 A 的时间给 B 的批次背书，正是今天这次事故的推理形态（"最近有一次成功"＋"库里有批" ≠ "这批是这次写的"）。

**★ ±120 秒只说明"时间接近"，不是"来源证明"。** 它能证明的仅限：`BettingCard.CapturedAt` 与某次采集的完成时刻相差不到 2 分钟。它**证明不了** `CapturedAt` 是哪段代码写的。要真正证明来源，需要采集侧把 `rec.FinishedAt` 直接作为 `CapturedAt` 一次写入（同一事务、同一个时间值），使配对从"±120 秒"变成"精确相等"。那是代码改动，本方案**不做**，只记为残余风险；在此之前 L1 的结论一律表述为"时间一致"，**不得写成"已证明写入来源"**。

由分层直接推出三条检验：

1. **手动采集永远拿不到绿**：`cards:manual` 过得了 L1，过不了 L2（`Kind` 不是 daily）。手点一次不会让闸以为本轮采过。
2. **迟到的成功等于没成功**：`rec.FinishedAt > runAt` 不算 L2（今天 16:46:12 那次对 16:40 轮无效），且其 `cap > runAt` 本身也不可用（未来批）。
3. **降级关闭后没有替代路径**：不存在"旧批再顶一次"，未达标直接红。代价必须写清：**cards 一失败当天就断榜**（今天 16:40 那轮按本版就是红，不是黄）。

### K2 判定（有序，命中即止；**唯一口径，降级已关闭**）

输入：`runAt`；`slot` = 当日 ≤ `runAt` 的最近一个 cards 时点（8:30 / 11:30 / 16:30 / 20:30）；`cap` = `MAX(BettingCard.CapturedAt)`（`Board='jc'`）；`rec` = **单一条**最近的成功采集记录（含 `Kind`、`FinishedAt`、`RowsAffected`、`jcRows`、`Message`）；`jcOk` = 该次 jc 板块是否真取到页面（§D 三态）；`complete` = `GetJcCaptureStateAsync` 完整性。

| # | 条件（自上而下，先中者胜） | 档 | verdict |
| --- | --- | --- | --- |
| 1 | `cap` 为空 | 红 | `no-batch` |
| 2 | `cap > runAt`（未来批） | 红 | `future-batch` |
| 3 | `rec` 为空，或 `|cap − rec.FinishedAt| > 120s` | 红 | `batch-mismatch` |
| 4 | `rec.Kind ≠ job:cards-daily`（只有手动采集） | 红 | `manual-only` |
| 5 | `rec.FinishedAt ∉ [slot, runAt]`（含迟到、含上一时点之前） | 红 | `no-capture-this-slot` |
| 6 | `rec` 达标但 `jcOk = false` | 红 | `jc-fetch-failed` |
| 7 | `rec` 达标、`jcOk`、`RowsAffected>0` 且 `complete` | 绿 | `fresh` |
| 8 | `rec` 达标、`jcOk`、`RowsAffected=0` 且 `[no-sale]` 证据齐（见 K2b） | 绿（空榜） | `no-sale` |
| 9 | `rec` 达标、`jcOk`，但 `complete=false` | 黄（**不发布**） | `partial` |
| 10 | `runAt` 与 `cap` 跨受注日（隔夜重算） | 跳过 | `cross-day-skip` |

关于 #10：**跨日不再凭 L1 重写**。隔夜重算既没有"本轮达标"，降级档也已关闭，所以一律不重写、不删票；但它也不是"该发而未发"，所以**不告警**，记 `Status='skipped'`、`Note='cross-day@<cap>'`。若确需隔夜出榜，走人工端点，不自动。

关于 #9：`partial` 与"批次新不新"无关。刚采到的新批也可能缺场/缺档，**新不新解决不了完整性问题**，所以不得因为"批次年轻"而放行。

### K2b NoSale 怎么落地（真 0 场，但不许沿用旧批）

**问题**：现有空结果**不更新 `CapturedAt`**（`UpsertCardsAsync` 空列表直接 `return 0`，`BettingRepository.cs:208-211`），所以"本轮竞彩 0 场"在 `BettingCard` 上没有痕迹，`cap` 还是旧批。若照常出榜，引擎 `GetJcSourceSnapshotAsync(runAt)` 读到的就是旧批场次——等于沿用旧批；若一律判"没采到"，真无在售的日子又永远不刷新，旧票会挂到隔天。

**N1 采集侧留证（不动表）**：jc 板块 `NoSale` 时，SyncLog 写一行 `Status=SUCCESS`、`RowsAffected=<bd+sfc>`、`Message='[no-sale] jc=0 bd=<n> sfc=<m> containers=jc:1;bd:1;sfc:1'`。**不写 `BettingCard`、不改 `CapturedAt`**（不伪造批次）。"本轮竞彩确实无在售"从此只由这一行证明。
- jc 容器不存在 → 不是 `NoSale`，是 `FetchFailed`（D2 挡板），记 `[fetch-failed]`。

**N2 闸的单列通道**：`no-sale` 只有下面全部成立才发绿：

- `Message` 前缀 `[no-sale]`、`jc=0`、`containers` 含 `jc:1`；
- **`cap` 自 `rec` 起未被改动**，且 `cap` 等于 `rec` 之前那一次成功采集的批次（旁证：本轮确实没写新批）。若 `cap` 在 `rec` 之后被改过 → 红 `batch-mismatch`（顺序矛盾，留给人看）；

**N3 出榜走"空列表形态"，不走常规取场次**：`no-sale` 时**不调用**常规出榜路径（会读旧批）。复用既有 `MilkBoardPlan` 第①形态（期号确认 + 采集完整 + 全被过滤 → 按过滤前受注日重写，空列表 = 撤失效旧票）：显式构造空 input slate → 写 0 注、撤上一轮未结算旧票、写 `FbMilkRunDate`、`Note='no-sale-jc'`。
这样"榜单清空"的依据是**本轮 0 场这个事实**，不是"拿旧批算出 0 票"。

### K3 四档（降级关闭后）：放行 / 告警不发布 / 拒绝 / 跳过

**① 放行（绿，无告警）** —— 两种，条件见 K2 #7 / #8：
- `fresh`：`rec` 同一条且达标、`jcOk`、`RowsAffected>0`、`complete`；
- `no-sale`：同一 `rec` 达标、`jcOk`、`jc=0` 且证据齐（K2b）、`cap` 未被改。**0 注对 0 行必须通过**。

**② 告警（黄，但"不发布"）** —— 只有 `partial` 一种：`rec` 达标且 `jcOk`，但 `complete=false`。
动作：**不写 `FbMilkRunDate`、不重写榜面、不删旧票**，`Status='failed'`、`Note='partial'`、`FailReason='partial:<cap>:<slot>'`，写 `high` 告警；入口返回"未发布"。（不新造状态词，沿用 `failed`。）
**调用者不得报发布成功**：cron 的 `RowsAffected` 记 0 并带原因；`RunTurnGuardAsync` 的 `Recalculated=false`；`RefreshNearKickoffAsync` 的 `Saved=0`。三处都不得把它写成 success。
★ 不得因批次年轻而放行——完整性跟新鲜度是两件事。

**③ 拒绝（红，榜面不动）** —— `no-batch` / `future-batch` / `batch-mismatch` / `manual-only` / `no-capture-this-slot` / `jc-fetch-failed`。
动作：**不写 `FbMilkRunDate`**、榜面停在上一轮、`Status='failed'`、`FailReason='<verdict>:<cap>:<slot>:degrade=off'`、写 `high` 告警。

**④ 跳过（灰，不告警）** —— `cross-day-skip`：不重写、不删票、不告警，`Note='cross-day@<cap>'`。它既不是"该发未发"，也不是"凭 L1 重写"。

必须说清：**拒绝不会让榜变新**，榜面仍是上一轮（可能基于更旧批次）的内容。拒绝唯一的收益是"不让更旧的覆盖"，所以红必须配告警，否则只是把"静默发旧批"换成"静默不刷新"。

### K4 关闭是显式开关，不是 `age ≤ 0`

- 常量：`MilkBatchGate.DegradeEnabled = false`。`MaxBatchAge` 字段保留但**关闭时不参与判定**（不读、不比较）。
- 判定里必须有一行显式分支：`if (!DegradeEnabled) return Red("no-capture-this-slot")`。**不得**依赖"把上限设成 0、让 `age ≤ 0` 自然不成立"这种隐式效果——那样改一个数字就能悄悄恢复降级，且日志上看不出来。
- `FailReason` 必须带 `degrade=off`，否则事后分不清"因关闭而拒"与"因超时而拒"。
- **今天 16:40 那轮**：`cap=15:25:15`（手动端点写的，当时**不留任何采集记录**），`rec` = 最近一条 cards 类成功记录 = `11:31:17`（daily）。`|cap − rec|` = 3h54m > 120s → 判 **红 `batch-mismatch`**，榜面保持 11:40 那轮。
- 就算 B 已上线、15:25 被记成 `cards:manual`：`cap` 与它对得上（过 L1），但 `Kind ≠ daily` → **红 `manual-only`**。两条路都到红，只是原因不同——这正是"分层比一个容差数字更能说清事"的地方。
- 代价必须承认：**当天 16:40 这轮不刷新**，页面停在 11:40 那轮，直到 20:30/20:40 才可能更新。

### K5 落点（修正 C4）
